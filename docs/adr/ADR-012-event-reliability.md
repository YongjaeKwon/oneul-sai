# ADR-012 이벤트 발행 · 소비 신뢰성: outbox · 멱등 소비자 · 다시 시도가 기본

- 날짜: 2026-10-07
- 상태: Accepted
- 관련 설계서: [SPEC-004 결제와 참가 확정](../specs/SPEC-004-payment.md) (0.1절 개발 승인 N · O, 리드 결정 기록 D3 · D4 · D5 · D7 · D8, 8절, 10절 "내부 구조", 16절 "검토한 대안")
- 관련 ADR: [ADR-005 동기 · 비동기 통신](./ADR-005-sync-vs-async.md) 결정 1 · 2 · Trade-offs, [ADR-006 Kafka](./ADR-006-why-kafka.md), [ADR-010 플랫폼 패키지](./ADR-010-platform-packages.md) 결정 1 · 3 · 6, [ADR-011 서비스 간 동기 호출](./ADR-011-service-to-service-calls.md) 결정 6, [ADR-001 모노레포](./ADR-001-why-monorepo.md)

## Context

Step 4에서 첫 Kafka 흐름이 생긴다. 운영자가 입금을 확인하면 payment-service가 결제 기록(payment_db `Payment`)을 남기고 `payment.completed.v1`을 발행하며, event-service가 그 이벤트를 받아 신청을 참가 확정으로 바꾼다(ADR-005 결정 2, SPEC-004 D3). 이 흐름에서 이벤트가 사라지거나 넘겨지면 참가자에게는 "입금했는데 입금 대기"로 보인다.

기존 ADR은 신뢰성을 구현 시점으로 미뤘다. ADR-006 결정은 "실제 비즈니스 이벤트를 구현하는 시점에는 Outbox 패턴 도입을 반드시 검토"하고 별도로 결정하라고 했고, ADR-005 Trade-offs는 이중 쓰기를 "초기엔 발행 실패 로깅 + 재발행 수단, 유실이 관측되면 outbox"로 유예했다. 모든 컨슈머의 이벤트 ID 기반 멱등 처리(ADR-005 Trade-offs)는 원칙만 있고 모양이 없다. `docs/events/README.md` 4절은 중복 · 재시도 · 순서 · DLQ · 발행 실패 · 커밋–발행 정합성을 "실제 구현 단계에서 결정"할 목록으로 두었다.

공유 코드의 자리도 정해야 한다. ADR-006은 "서비스 간 이벤트 발행/구독의 공통 코드는 `packages/kafka`에"(ADR-006:26)라고 했지만, ADR-010 결정 1 · 6의 플랫폼 패키지 목록은 logger · config · service-kit뿐이다. 클라이언트 라이브러리도 아직 없다 — `packages/kafka/README.md`는 kafkajs를 계획으로 적었을 뿐이다.

## Decision

**1. 발행은 transactional outbox + 같은 프로세스의 폴링 relay다(at-least-once).** 발행하는 서비스는 자기 DB의 `OutboxEvent`(id = 봉투 `eventId`)를 업무 행(Step 4는 `Payment`)과 **한 트랜잭션**에 넣는다. relay는 `publishedAt IS NULL`인 행을 오래된 순으로 **잠금 없이** 읽어 보내고(`acks: -1`) `publishedAt`을 쓴다 — 잠금을 쥔 채 네트워크 전송을 기다리지 않는다(ADR-011 결정 4의 태도). 보낸 뒤 표시 전에 죽으면 다시 보내고, 중복은 소비자 멱등(결정 2)이 흡수한다.

- **단일 실행**: 한 회차는 앞 회차가 끝난 뒤 `setTimeout`으로 예약한다(겹쳐 돌지 않는다) — 평소 1초, 실패하면 5초 뒤.
- **전송 제한 시간**: producer 전달 제한 시간은 10초다(librdkafka `message.timeout.ms`). 넘으면 실패로 보고 warn `outbox.publish_failed`(eventId · 에러 이름 · 코드)를 남긴다. 행이 남아 있는 한 relay가 끝없이 다시 보낸다.
- **치명적 에러**: relay · 소비 루프에서 잡히지 않은 에러와 클라이언트의 치명적 에러는 error 로그 뒤 프로세스를 끝내 다시 시작되게 한다. 브로커 연결 끊김은 치명적 에러가 아니다 — 클라이언트가 다시 연결한다.
- **Kafka 없이도 뜬다**: relay와 소비자는 `main.ts`에서만 시작한다(`createApp`에 넣지 않아 통합 테스트가 Kafka 없이 돈다). 시작할 때의 연결 · `createTopics` · 구독 실패는 치명적 에러가 아니다 — 소비 루프는 warn `event.consumer_start_failed` 뒤 5초 쉬고 시작을 처음부터 다시 하고, relay는 보낼 행이 있을 때 연결하므로 연결 실패가 곧 전송 실패다(warn 뒤 5초). 어느 쪽도 프로세스를 끝내지 않고 HTTP는 계속 응답한다.

이것이 ADR-006 결정이 미룬 "Outbox 도입" 결정이고, ADR-005 Trade-offs의 이중 쓰기 유예를 거둔다 — 첫 흐름부터 outbox로 시작한다.

**2. 소비자는 이벤트 ID로 멱등하다.** 소비하는 서비스는 자기 DB의 `ProcessedEvent`(`eventId` PK)를 상태 변경과 **같은 트랜잭션**에 넣는다. 순서: `ProcessedEvent` INSERT(`ON CONFLICT DO NOTHING` — 넣은 행이 0이면 이미 처리한 이벤트라 아무것도 바꾸지 않고 커밋) → 대상 행 잠금 → 업무 판정 → UPDATE → DB 커밋 → 오프셋 커밋(`autoCommit: false`, 수동). `ProcessedEvent`는 지우지 않는다.

- **처음부터 읽기**: 소비자는 그룹의 커밋된 오프셋이 없으면 처음부터 읽는다(`fromBeginning: true` = earliest). 중복은 `ProcessedEvent`가 거른다.
- **토픽 준비**: 소비 루프는 구독 전에 admin `createTopics`로 토픽을 한 번 만든다(이미 있으면 그대로). 운영 토픽의 명시 생성 · 파티션 수 · 보존 기간 · 권한(ACL)은 결정 예정 (Step 8).

**3. 소비 실패의 기본값은 "커밋하지 않고 다시"다.** 넘기는(커밋하는) 것은 해석할 수 없는 메시지뿐이다.

| 분류              | 예                                                                                                                                           | 처리                                                                                             | 오프셋        |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------------- |
| 업무 판정         | 대상이 이미 바뀜 · 취소됨 · 없음 등 소비자 판정표의 결과(SPEC-004 6절)                                                                       | 에러가 아니다 — `ProcessedEvent` 기록 · 로그                                                     | 커밋          |
| 해석 불가(독)     | JSON 아님 · 봉투/payload Zod 실패 · `type` 다름 · `version` 다름                                                                             | error `event.rejected`(topic · partition · offset · 읽을 수 있으면 eventId)                      | 커밋(넘김)    |
| 그 밖의 모든 에러 | 잠금 대기 · 교착 · DB 연결 · 마이그레이션보다 먼저 뜬 소비자 · 무결성 위반(코드 결함) · 알 수 없는 예외 — 종류를 가르지 않는다(SPEC-004 8절) | 같은 메시지를 그 자리에서 다시 — 5초 간격, 끝없이. warn `event.retrying`, 10번째부터 error(알람) | 커밋하지 않음 |

"그 밖" 에러 동안 그 파티션의 뒤 메시지는 기다린다. 트랜잭션이 롤백되어 `ProcessedEvent`가 남지 않으므로, 코드 결함이면 고쳐 배포하는 것만으로 이어서 처리된다.

**4. DLQ 토픽은 두지 않는다 — outbox가 재생 원천이다.** 해석 불가로 넘긴 이벤트의 원본은 발행한 서비스의 outbox에 남아 있어 `publishedAt = NULL`로 다시 보낸다(개발자 절차 — SPEC-004 9절 "점검 쿼리 · 개발자 절차", `docs/database/README.md`에 적는다). 외부 부수 효과가 있는 소비자(Step 7 알림)가 생길 때 다시 본다.

**5. 순서는 소비자가 기대지 않는다.** 토픽 사이의 순서는 없고(토픽 = 이벤트 이름 + 버전), **같은 키 안에서도 발행 순서가 커밋 순서와 같다고 보장하지 않는다** — relay는 `createdAt` 순으로 읽는데 `createdAt`은 행을 INSERT할 때 정해지고 커밋 시각이 아니라서, 늦게 커밋된 행이 더 이른 `createdAt`을 가지고 뒤에 나갈 수 있다. **소비자는 도착 순서가 아니라 대상의 지금 상태로 판정한다.** 파티션 키는 소비자가 대상을 찾을 키다(`payment.completed.v1`은 `applicationId`). 같은 토픽에 이벤트를 더하는 다음 소비자도 이 규칙을 따른다.

**6. 봉투에 `requestId?`를 싣는다.** `EventEnvelope`에 선택 필드 `requestId`(UUID)를 두고, 발행을 일으킨 요청의 `x-request-id`가 UUID 모양일 때만 싣는다(Gateway는 클라이언트 값을 검사 없이 넘긴다). 소비자는 이 값을 로그에 이어 붙인다 — ADR-005 Trade-offs "x-request-id를 이벤트 메타데이터에 실어 전 구간 로그를 이어 붙이는 규약"의 구현이다. 봉투 Zod 스키마(`eventEnvelopeSchema(payload)`)는 contracts에 둔다.

**7. `packages/kafka`는 플랫폼 코드만 둔다 — ADR-010 결정 1 · 6을 넓힌다.**

- 담는 것: 연결 설정 타입, 클라이언트 만들기(`createKafka` — 브로커 · clientId · 로그 연결), 토픽 이름(`buildTopicName(type, version)` 하나 — 이벤트 이름 + 버전), 봉투 직렬화 · 해석(`encodeEnvelope` · `decodeEnvelope(value, event, payloadSchema)` — 기대하는 `{ type, version }`은 부르는 쪽이 contracts 상수로 넘긴다. 패키지는 값을 비교만 하고 이벤트 종류를 알지 못한다), 라이브러리 타입 별칭. 클라이언트 의존성은 이 패키지에만 설치하고, 앱은 라이브러리를 직접 import하지 않는다.
- 담지 않는 것: payload Zod 스키마 · 이벤트 이름 · 버전 상수(contracts), outbox 테이블 · relay · 소비 판정(각 서비스 — Prisma를 쓰므로 공유 패키지에 둘 수 없다).
- **ADR-010 결정 1 · 6의 플랫폼 패키지 목록에 `@oneul-sai/kafka`를 더한다.** ADR-010 결정 3의 편입 기준 1~3(DB · Prisma 금지, env 금지, 프로토콜 밖 도메인 enum 금지)은 그대로 적용한다. 기준 4("두 서비스 이상이 같은 동작을 요구할 때만")는 **한 프로토콜의 양 끝 — 봉투 부호화 · 해석, 같은 연결 설정 — 을 한 동작으로 본다.** 발행 쪽(payment)과 소비 쪽(event)이 같은 봉투 규칙을 집행하는 것이 이 패키지의 존재 이유다. 한 서비스만 쓰는 Producer/Consumer 래퍼는 넣지 않는다.
- 기준 1 · 2는 기계로 막는다: service-kit과 같은 `no-restricted-imports`(Prisma) · `no-restricted-properties`(`process.env`) 규칙을 `packages/kafka/eslint.config.js`에 둔다.
- AGENTS.md 3절 원칙 4 · 9장의 플랫폼 패키지 목록은 이 ADR을 근거로 kafka를 더한다.

**8. 클라이언트는 `@confluentinc/kafka-javascript` `1.10.1`(정확히 고정)이다.** `packages/kafka` 한 곳에 설치하고 `pnpm-workspace.yaml`의 `allowBuilds`에 `'@confluentinc/kafka-javascript': true`를 더한다. API는 KafkaJS 호환 모양(`KafkaJS` 이름 내보내기)을 쓴다. Node 하한(22.12)은 그대로다. 비용과 확인 항목은 `docs/architecture/tech-stack.md` 함정 12.

**9. 기존 ADR 문장의 해석.** 아래 문장들은 뒤집히지 않았다 — 상태 줄은 그대로 `Accepted`이고, 이 ADR이 Step 4에서의 뜻을 적는다.

- **ADR-005 결정 1 "참가 신청 확정 … 사용자가 응답을 기다리는 경로"**: 신청 접수와 정원 판정(SPEC-003)이 동기 경로다. 입금 확인 뒤의 참가 확정은 결정 2의 비동기(`payment.completed` → 참가 확정)다.
- **ADR-005 Trade-offs "확정 대기"**: 새 상태가 아니다. 결제는 기록됐고 신청은 아직 입금 대기인 구간이며, 운영자 화면이 "입금 확인됨 · 참가 확정 반영 중"으로 드러낸다(SPEC-004 D3 · D15 — "시차를 숨기지 않고 드러낸다").
- **ADR-005 Trade-offs 이중 쓰기 유예**: 거둔다 — 결정 1.
- **ADR-006 배경 "신청 확정 시 결제 요청"**: 수동 입금에는 "결제 요청" 단계가 없다. 신청의 입금 대기가 그 역할을 하고, 결제는 `COMPLETED`로 태어난다(SPEC-004 D1). 신청 쪽 이벤트(`application.*`)는 발행하지 않는다(구독자가 없다 — SPEC-004 D7). PG 단계의 요청 · 실패 상태는 SPEC-004 9절 "PG 때 더할 것".
- **ADR-011 결정 6의 "호출자 문맥 없는 서비스 간 조회(Step 4 결제 이벤트 소비자)"**: Step 4에는 생기지 않는다. payment-service는 신청을 조회하지 않고, 소비자는 신청의 존재 · 회원 · 상태를 자기 DB에서 판정한다(SPEC-004 D3). 남는 것은 Step 7(알림 받는 사람의 정보)이다.
- **ADR-001:16 "환불 → 정원 반환"**: 서술이다. 정원 반환은 신청 취소가 하고, 환불 기록은 event 쪽에 바꿀 것이 없다(신청은 이미 취소됨 — SPEC-004 D11).

## Reason

**유실은 outbox가 가장 싸게 막는다.** "커밋 뒤 직접 발행 + 실패 로그 + 재발행 수단"(ADR-005의 초기안)으로 "무엇이 발행 안 됐나"를 알려면 결국 미발행 표시가 필요한데, 그것이 곧 payload 없는 outbox다. 게다가 커밋과 발행 사이에 죽으면 표시도 못 남긴다. outbox는 테이블 하나 + 타이머 하나이고 새 인프라가 없으며, `publishedAt = NULL`이 재발행 수단이다.

**잠금 없이 읽고, 겹쳐 돌지 않고, 10초 안에 실패를 드러낸다.** 잠금을 쥔 채 전송하면 행 잠금과 DB 연결을 네트워크 너머로 쥔다. `setInterval`이면 앞 회차가 끝나지 않았는데 다음 회차가 같은 행을 두 번 보낸다. 라이브러리 기본 전달 제한 시간(5분)이면 브로커가 멈췄을 때 전송 한 번이 몇 분 걸려 `outbox.publish_failed`가 돌지 않고, `/health`는 DB만 보므로 아무 신호가 없다. ADR-011 결정 4의 3초는 HTTP 호출 값이고 브로커 전달은 재시도를 포함하므로 10초다.

**브로커 없이 뜨는 것은 개발 · CI의 전제다.** 시작할 때의 연결 실패까지 치명적으로 보면 브로커 없는 CI `e2e` 잡과 기본 로컬(`docker compose up -d`)에서 서비스가 뜨지 못한다. 입금 기록 · 신청 같은 HTTP 경로가 브로커 가용성에 묶일 이유도 없다.

**멱등은 이벤트 ID로, 판정은 상태로.** `ProcessedEvent`는 ADR-005 "모든 컨슈머는 이벤트 ID 기반 멱등 처리"를 글자 그대로 충족하고, 효과가 멱등이 아닌 다음 소비자에도 같은 모양이다. 같은 eventId가 동시에 두 번 와도 PK 삽입이 직렬화한다. 상태 검사는 어차피 필요한 업무 판정이다.

**처음부터 읽지 않으면 조용히 건너뛴다.** 라이브러리 기본값(latest)이면 커밋된 오프셋이 없는 그룹(로컬 브로커 재생성 · 스모크의 새 그룹, 뒤에 CI 브로커 · 운영 첫 배포)은 참가 전에 쌓인 이벤트를 건너뛰고, outbox는 이미 "보냄"이라 무엇을 재생할지도 모른다. 토픽을 소비자 코드가 만들면 어느 환경에서나 같은 한 줄이다 — librdkafka 소비자는 구독만으로 토픽을 만들지 않는다(외부 지식 — SPEC-004 17절 5번 PR에서 확인).

**넘기는 것이 다시 시도보다 비싸다.** "알려진 일시 에러만 다시, 나머지는 넘김"이면 목록 밖 일시 에러(DB 재시작 중 · 연결 수 초과 · 소켓 에러)와 배포 순서 사고(마이그레이션 전 소비자)가 입금 확인을 넘겨 버리고, 그 확정은 사람의 재생 없이는 일어나지 않는다. 다시 시도는 다시 받아도 결과가 같은 메시지(해석 불가)만 빼면 손대지 않아도 이어진다. 파티션이 멈추는 대가는 Step 4 양(회차당 14건 수준)에서 받아들인다.

**DLQ는 지금 원본을 하나 더 만들 뿐이다.** 원본이 이미 outbox에 있고 재생 절차가 있다. DLQ 토픽은 소비 · 재생 도구를 하나 더 요구한다.

**순서를 약속하지 않는 것이 정직하다.** outbox relay는 커밋 순서를 알 수 없다. 약속할 수 없는 순서에 기대는 소비자보다, 지금 상태로 판정하는 소비자가 중복 · 지연 · 재생 모두에서 같은 결과를 낸다.

**`packages/kafka`는 ADR-006의 자리를 지키면서 업무 규칙을 넣지 않는다.** 봉투 부호화 · 해석이 두 벌이면 발행 쪽과 소비 쪽이 따로 고쳐져 어긋난다. 무엇을 확정하는지 같은 판정은 서비스에 남긴다. 라이브러리를 바꿀 때 고칠 곳은 패키지 하나 + 서비스 두 곳(relay · 소비자)이다. 편입 기준을 새로 정의하지 않고 ADR-010 기준을 그대로 쓰되, 기준 4의 "같은 동작"이 프로토콜의 양 끝을 포함한다고만 적는다.

**클라이언트는 지금 Node 하한에서 도는 유지보수 중인 것이 이것 하나다(2026-09-29 조사).** librdkafka 2.15.1 기반이라 로컬 `apache/kafka:4.0.0`(KRaft)과 맞고, 생성 시 `autoCommit: false` + `commitOffsets`, `acks: -1`이 있으며, API가 KafkaJS 모양이라 저장소의 계획과 가장 가깝다. v1.10.1에 Node 22용 미리 빌드한 바이너리가 Windows x64 · linux-glibc-x64 · linux-musl-x64에 있다.

## Trade-offs

- **네이티브 애드온이다.** `allowBuilds`가 없으면 pnpm 11 `strictDepBuilds`로 설치가 실패한다. 설치할 때(CI · Docker 빌드 포함) GitHub 릴리스에서 바이너리를 받고, 못 받으면 소스 빌드로 넘어가 도구 없는 alpine 빌더에서 실패한다. 라이브러리 README는 pnpm 지원을 "experimental"로 적었다. Windows · CI · Docker 세 곳의 설치 확인은 SPEC-004 17절에 적는다.
- **"그 밖" 에러가 코드 결함이면 그 파티션이 멈춘다.** 고쳐 배포할 때까지 뒤 메시지도 기다린다. 10번째 재시도의 error 알람과 운영자 화면의 "바뀌지 않았습니다"가 드러낸다.
- **relay는 단일 실행이다.** 같은 서비스의 프로세스가 여럿이면 각자 relay를 돌려 같은 행을 두 번 보낼 수 있다 — 소비자 멱등이 흡수한다. 행 잠금으로 나누는 방법(`FOR UPDATE SKIP LOCKED`)은 아래 Alternatives에서 기각했다.
- **넘긴 메시지 · 유실된 확정의 복구는 사람 손이다.** 해석 불가로 넘긴 이벤트는 개발자가 outbox 재생으로 다시 보낸다. 발행 지연 경보 · 소비 지연 모니터링은 결정 예정 (Step 8).
- **`ProcessedEvent`는 지우지 않는다.** 행이 계속 는다(지우면 브로커에 남은 메시지나 재생이 되돌린 확정을 다시 만든다). outbox 행은 결제 기록의 보관 · 파기 규칙(SPEC-004 ★F F-2)을 따른다 — 결제를 파기할 때 함께 지우고, 재생 기간이 지난 행은 지운다. 재생 기간 · 정리 주기는 결정 예정 (Step 8), 그때까지는 지우지 않는다(SPEC-004 9절 "보존").
- **운영 구성은 이 ADR 밖이다.** 운영 브로커 · 토픽 명시 생성 · 자동 생성 끄기 · ACL · 인증은 결정 예정 (Step 8).

## Alternatives

**커밋 뒤 직접 발행 + 실패 로그 + 재발행 도구(ADR-005 Trade-offs의 초기안) — 기각.** 테이블이 하나 적다. 미발행 표시가 필요해 사실상 payload 없는 outbox가 되고, 커밋과 발행 사이에 죽으면 표시도 못 남긴다.

**CDC(Debezium) — 기각.** 앱 코드가 가장 적지만 새 인프라 · 운영이다(AGENTS.md 원칙 6).

**relay가 `SELECT … FOR UPDATE SKIP LOCKED` 트랜잭션 안에서 전송 — 기각.** 프로세스 여럿의 중복이 없다. 대신 행 잠금과 DB 연결을 네트워크 너머로 쥔다.

**relay를 `setInterval`로 · 전송 제한 시간을 라이브러리 기본값으로 — 기각.** 회차가 겹쳐 같은 행을 두 번 보내고, 브로커가 멈추면 실패가 몇 분 늦게 드러난다.

**따로 도는 미발행 점검 타이머 · 시도 횟수 · 마지막 에러 열 · 두 배 간격 — 기각.** 10초 제한 시간이 장애를 이미 `outbox.publish_failed`로 드러내고, 행이 남아 있는 한 유실이 없다. 발행 지연 경보는 Step 8.

**시작할 때의 브로커 연결 실패도 프로세스를 끝내기 — 기각.** 재시작 반복이 장애를 드러내지만, 브로커 없는 CI `e2e` 잡 · 기본 로컬에서 서비스가 뜨지 못하고 로컬 `tsc-watch`는 다시 띄우지 않는다.

**소비자 멱등을 상태 검사만으로 — 기각.** 테이블이 없다. ADR-005 "이벤트 ID 기반 멱등"의 문구와 다르고, 다음 소비자마다 따로 증명해야 한다.

**소비자를 라이브러리 기본값(latest)으로 — 기각.** 그룹 오프셋이 없는 새 환경에서 앞선 이벤트를 조용히 건너뛰고, 재생 대상을 모른다.

**알려진 일시 에러만 다시 시도하고 나머지는 넘김 · 무결성 위반만 넘김 — 기각.** 파티션이 멈추지 않는다. 목록 밖 에러 · 코드 결함이 확정을 넘겨 버려 재생이 있어야 확정된다.

**토픽 준비를 CI 단계 · 온보딩 명령으로 — 기각.** 코드가 없다. 환경마다 손이 가고, 빠뜨리면 첫 확정이 늦거나 사라진다.

**DLQ 토픽 — 지금은 기각.** 원본이 outbox에 있다. 외부 부수 효과가 있는 소비자(Step 7)가 생길 때 다시 본다.

**Kafka 상태를 `/health`에 — 기각.** 브로커 장애가 프로브 실패 → 재시작으로 번져 입금 기록 · 신청까지 막는다.

**`packages/kafka`에 래퍼를 두지 않고 서비스마다 클라이언트를 직접 — 기각.** 패키지가 가볍다. ADR-006:26과 달라 또 다른 ADR이 필요하고, 라이브러리를 바꿀 때 두 서비스를 따로 고친다.

**Producer/Consumer 클래스 래퍼를 `packages/kafka`에 — 기각.** relay와 소비 루프는 한 서비스씩만 쓰는 동작이다(ADR-010 기준 4).

**토픽 이름 상수를 contracts에도 — 기각.** `buildTopicName`과 두 벌이 된다.

**ADR-005 · 006 · 010 · 011 상태 줄에 "일부 대체 · 해석"을 적기 — 기각.** 어디서 무엇이 바뀌었는지 한눈에 보이지만, `docs/adr/README.md`의 상태 규칙(`Superseded by`뿐)에 없는 형식이고 뒤집힌 결정도 없다. 연결은 이 ADR의 "관련 ADR"과 문서들이 한다.

**클라이언트 — `@platformatic/kafka@2.12.1` — 기각.** 순수 TS · ESM이고 빌드 스크립트가 없지만 Node 하한을 `>=22.22`로 올려야 한다(툴체인 변경).

**클라이언트 — `kafkajs@2.2.4` — 기각.** 마지막 릴리스가 2023-02로 유지보수가 멈췄고, Kafka 4.0 KRaft에서 소비자 그룹 실패 보고가 있다.

**클라이언트 — `@nestjs/microservices` Kafka transport — 기각.** 내부에서 kafkajs를 불러오고, 추상화가 한 겹 는다.
