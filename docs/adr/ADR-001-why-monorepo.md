# ADR-001 왜 모노레포인가 (pnpm workspace + Turborepo)

- 날짜: 2026-09-22
- 상태: Accepted

## Context

오늘 사이는 오프라인 로테이션 소개팅 서비스다. 참가자는 웹/모바일 앱에서 이벤트를 신청하고, 운영자는 어드민에서 이벤트를 개설·관리하며, 현장에서는 로테이션(테이블 이동) 진행이 실시간으로 돌아가고, 이벤트 종료 후 상호 선택 결과로 매칭이 확정되면 알림이 나가고, 참가비 결제·환불이 이 흐름 전체에 얽혀 있다.

이 도메인의 특성상 코드베이스는 처음부터 여러 실행 단위로 쪼개진다. 사용자용 웹(web), 운영자용 어드민(admin), 모바일 앱(mobile), 그리고 API 게이트웨이 뒤의 백엔드 서비스들 — 회원(member), 이벤트(event), 매칭(matching), 알림(notification), 결제(payment) — 까지 앱이 9개다. 여기에 공유 계약(contracts), 공용 설정(typescript-config, eslint-config) 등 패키지가 11개 붙는다.

문제는 이 단위들이 물리적으로는 분리되어 있어도 논리적으로는 강하게 결합되어 있다는 점이다. 예를 들어:

- 이벤트 정원과 동시 신청 처리 규칙이 바뀌면, event-service의 API 응답 스키마, 게이트웨이의 프록시 계약, 웹/모바일의 신청 화면, 어드민의 정원 관리 화면이 한 번에 바뀌어야 한다.
- 매칭 확정 이벤트의 페이로드가 바뀌면 matching-service(발행), notification-service(구독), 그리고 결과를 보여주는 프런트엔드가 같은 커밋 안에서 맞춰져야 한다. 매칭 알림이 잘못된 상대 정보를 담고 나가는 것은 이 서비스에서 가장 치명적인 장애 유형 중 하나다.
- 결제 상태(결제 완료 → 신청 확정, 환불 → 정원 반환)는 payment-service와 event-service 양쪽의 상태 전이에 걸쳐 있어, 계약이 어긋나면 정원 계산 자체가 틀어진다.

팀은 소규모다. 서비스별로 리포지토리를 나누고 각자 오너를 두는 구조를 감당할 인원이 아니며, 한 사람이 하루에 프런트엔드와 백엔드 서비스 두세 개를 오가며 작업하는 것이 일상이 될 것이다.

이 조건에서 리포지토리 구조를 결정해야 한다.

## Decision

**단일 리포지토리(모노레포)를 채택한다.** 도구는 **pnpm workspace**(패키지 연결·의존성 관리)와 **Turborepo**(태스크 실행·캐시)를 사용한다.

- 루트 아래 `packages/apps/*`에 앱 9개(web, admin, mobile, api-gateway, member-service, event-service, matching-service, notification-service, payment-service), `packages/*`에 공유 패키지 11개(contracts, typescript-config, eslint-config 등)를 둔다.
- API/이벤트 계약은 `@oneul-sai/contracts` 패키지에 zod 스키마 + TypeScript 타입으로 정의하고, 모든 앱이 `workspace:*`로 참조한다.
- 빌드·린트·타입체크·테스트는 루트 turbo.json의 태스크 계약(dev, build, start, lint, typecheck, test, db:generate)으로 통일하고, 각 패키지는 필요한 스크립트만 선언한다.
- 각 앱/서비스는 독립적으로 실행·배포 가능해야 한다. Docker 이미지는 `turbo prune`으로 해당 앱과 그 의존 패키지만 잘라낸 서브셋에서 빌드한다. 모노레포는 코드 배치의 결정이지 배포 단위의 결정이 아니다.

## Reason

**1. 계약 공유와 타입 안전성이 이 도메인에서 특히 중요하다.** 신청 → 결제 → 정원 확정 → 로테이션 → 상호 선택 → 매칭 → 알림으로 이어지는 흐름은 서비스 경계를 다섯 번 이상 넘는다. 경계마다 스키마가 문서로만 존재하면, "이벤트 정원이 남았는지"의 판단 기준이나 "매칭 확정" 페이로드의 필드가 서비스마다 미묘하게 다른 상태로 배포될 수 있다. contracts 패키지를 단일 소스로 두고 모두가 같은 커밋의 같은 타입을 import하면, 계약 위반이 런타임 장애가 아니라 typecheck 실패로 잡힌다.

**2. cross-cutting 변경의 원자성.** 위 Context의 예시처럼 이 프로젝트의 의미 있는 변경은 대부분 3개 이상의 패키지에 걸친다. 모노레포에서는 이것이 PR 하나, 리뷰 하나, 배포 판단 하나다. polyrepo였다면 계약 패키지 버전 올리기 → 각 리포에서 버전 범프 PR → 순서 맞춰 머지라는 절차가 변경마다 반복되고, 그 절차의 중간 상태(일부 서비스만 새 계약을 아는 상태)가 프로덕션에 존재하게 된다.

**3. 통합 CI와 Turborepo 캐시.** 앱 9개 + 패키지 11개를 매 커밋마다 전부 빌드·테스트하는 것은 소규모 팀의 CI 예산으로 감당하기 어렵다. Turborepo는 태스크 그래프와 입력 해시 기반 캐시로 바뀐 패키지와 그 영향권만 다시 실행한다. web만 고친 커밋에서 payment-service 테스트가 다시 돌지 않는다는 것이 이 구조가 스케일하는 전제다.

**4. 소규모 팀의 운영 비용.** 리포지토리가 하나면 툴링 설정(Prettier, ESLint, tsconfig, CI 파이프라인)도 한 벌이다. 실제로 shared config 패키지 두 개로 20개 패키지의 설정을 통일하고 있다. polyrepo에서 이것은 리포 수만큼 복제되고, 복제된 것은 반드시 드리프트한다.

**5. 독립 배포 가능성은 포기하지 않는다.** 서비스별 DB 분리(member_db, event_db, …)와 게이트웨이 프록시 구조는 유지되며, `turbo prune` 기반 Docker 빌드로 각 서비스는 자기 의존성만 담은 이미지로 따로 배포된다. 코드가 한 리포에 있다는 것과 함께 배포된다는 것은 별개다.

## Trade-offs

솔직하게 적어둔다.

- **리포지토리가 사실상 단일 장애점이 된다.** CI 설정이 깨지거나 공유 패키지(특히 contracts)에 잘못된 변경이 들어가면 전체 팀의 작업이 막힌다. polyrepo라면 국소화됐을 문제다. contracts 변경에는 리뷰를 더 엄격하게 적용하는 것으로 완화한다.
- **"한 커밋에 다 고친다"는 장점은 "다 고치기 전엔 머지 못 한다"는 뜻이기도 하다.** 계약 변경이 6개 패키지를 건드리면 PR이 커지고 리뷰가 무거워진다. 점진적 마이그레이션(구/신 필드 병행)이 필요한 경우 모노레포라고 해서 절차가 사라지지는 않는다.
- **도구 버전의 일괄 관리 강제.** TypeScript, ESLint 같은 핵심 도구를 패키지별로 다른 메이저 버전으로 쓰기 어렵다. 업그레이드는 전체가 한 번에 움직여야 하고, 한 패키지의 호환성 문제가 전체 업그레이드를 지연시킬 수 있다.
- **Turborepo 캐시의 정확성은 입력 선언에 달려 있다.** turbo.json의 inputs/outputs를 부정확하게 선언하면 stale 캐시로 "빌드는 통과했는데 실제론 깨진" 상태가 생길 수 있다. 캐시 설정 자체가 유지보수 대상이다.
- **git 히스토리와 체크아웃이 무거워진다.** 20개 패키지의 커밋이 한 히스토리에 섞이므로 특정 서비스의 변경 추적에는 경로 필터가 필요하다. 현재 규모에서는 문제가 아니지만, 규모가 커지면 sparse checkout 등의 대응이 필요해질 수 있다.
- **접근 제어 단위가 리포지토리 전체다.** 결제 코드만 접근을 제한하는 식의 리포 단위 권한 분리는 불가능하다. 현재 팀 규모에서는 필요 없는 기능이지만, 외주나 파트너 협업이 생기면 제약이 된다.

## Alternatives

### Polyrepo (서비스/앱별 리포지토리 분리) — 기각

각 서비스가 완전한 자율성을 갖고, 리포 단위 권한 분리와 독립적인 도구 선택이 가능하다. 그러나 계약 공유가 npm 패키지 퍼블리시 + 버전 범프 절차가 되면서 **계약 버전 드리프트**가 구조적으로 발생한다. "matching-service는 contracts 1.3을 쓰는데 notification-service는 1.2를 쓰는" 상태가 절차상 자연스러운 중간 상태가 되고, 이 프로젝트에서 그 드리프트의 결과는 잘못된 매칭 알림이나 정원 계산 오류다. 버전 관리·릴리스 파이프라인·리포별 CI를 유지할 인력도 없다. 서비스 팀이 여럿으로 나뉘고 각자 오너십을 가질 규모가 되면 재검토할 수 있으나, 지금은 비용만 있고 이득이 없다.

### Nx — 기각

기능은 Turborepo의 상위 호환에 가깝다. 프로젝트 그래프, affected 계산, 분산 캐시에 더해 코드 생성기와 플러그인 생태계까지 제공한다. 그러나 그만큼 무겁고 규약이 강하다. executor/generator 체계를 따르면 각 패키지의 빌드 방식이 Nx 플러그인에 결합되고, Next.js·NestJS·Expo·Prisma가 섞인 이 스택에서 플러그인 버전 호환성 관리가 별도의 일이 된다. Turborepo는 "package.json scripts를 그대로 두고 실행·캐시만 관장"하는 얇은 계층이라, 각 프레임워크의 표준 CLI(next build, nest build, expo)를 그대로 쓸 수 있고 나중에 걷어내기도 쉽다. 환경 구축 단계에서 필요한 것은 태스크 오케스트레이션과 캐시뿐이므로 더 얇은 쪽을 택했다.

### Lerna — 기각

역사적으로 표준이었으나 현재는 유지보수 주체가 바뀐 뒤 태스크 실행을 사실상 Nx에 위임하는 방향으로 축소되었고, 독자적인 가치는 버전 관리·퍼블리시 워크플로에 남아 있다. 이 프로젝트의 패키지는 전부 private이고 npm 퍼블리시 계획이 없으므로 Lerna의 남은 강점이 쓰일 곳이 없다. 워크스페이스 연결은 pnpm이, 실행·캐시는 Turborepo가 더 잘한다.

### pnpm workspace 단독 (Turborepo 없이) — 기각

가장 얇은 구성이다. `pnpm -r --filter`로도 선택 실행은 가능하다. 그러나 태스크 간 의존성(contracts를 먼저 빌드해야 서비스 typecheck가 가능)과 캐시가 없어, 패키지가 20개인 시점부터 CI 시간과 로컬 반복 속도가 선형으로 나빠진다. Turborepo의 추가 비용은 turbo.json 파일 하나 수준으로 충분히 작다.
