# ADR-008 Kubernetes 배포 전략: Kustomize 중심, Helm은 서드파티 설치 전용

- 날짜: 2026-09-22
- 상태: Accepted

## Context

오늘 사이는 오프라인 로테이션 소개팅 서비스이고, 백엔드는 api-gateway, member-service, event-service, matching-service, notification-service, payment-service의 6개 서비스로 분리되어 있다. 이 서비스들은 결국 하나의 Kubernetes 네임스페이스(`oneul-sai`)에 함께 배포될 예정이며, 각 서비스는 거의 동일한 형태의 리소스 묶음 — Deployment, Service, ConfigMap, Secret — 을 필요로 한다.

배포 대상 워크로드의 성격을 보면 요구사항이 단순하지 않다. 이벤트 신청 오픈 시점에는 정원이 한정된 이벤트에 동시 신청이 몰리므로 event-service와 api-gateway는 순간 트래픽을 받아낼 수 있어야 하고, 필요하면 수평 확장(HPA)이 가능해야 한다. 현장 로테이션 진행 중에는 event-service가 잠깐이라도 죽으면 진행자와 참가자가 바로 체감하므로, 롤링 업데이트 중에도 준비되지 않은 파드로 트래픽이 가지 않도록 Readiness Probe가 정확해야 한다. 매칭 발표 직후에는 notification-service가 알림을 몰아서 보내고, payment-service는 결제라는 특성상 배포 중 중단 시간이 곧 매출 손실과 신뢰 문제로 이어진다. 즉 "6개의 비슷한 서비스"이지만 배포·가용성 요구는 서비스마다 결이 다르고, 이것을 환경(local/dev/prod)별로 다르게 조정할 수 있어야 한다.

한편 인프라에는 우리가 작성하지 않는 서드파티 구성요소(Kafka, Prometheus 등)도 올라간다. 이들은 커뮤니티가 관리하는 복잡한 설치물이며, 우리가 매니페스트를 직접 유지보수할 이유가 없다.

현재 단계는 환경 구축 단계다. 실제 클러스터 배포는 아직 하지 않으며, 지금 결정해야 하는 것은 "매니페스트를 어떤 도구와 구조로 관리할 것인가"이다.

## Decision

- 자체 서비스 6개의 Kubernetes 매니페스트는 **Kustomize**로 관리한다. `base/`에 서비스별 공통 매니페스트(Deployment, Service, ConfigMap, Secret)를 두고, `overlays/local`, `overlays/dev`, `overlays/prod`에서 replica 수, 리소스 요청/제한, 이미지 태그, 환경 변수 등을 패치한다.
- **Helm은 서드파티 구성요소(Kafka, Prometheus 등) 설치 전용**으로만 사용한다. 자체 서비스를 Helm 차트로 템플릿화하지 않는다. 하나의 대상에 두 도구를 겹쳐 쓰지 않는 것이 원칙이다.
- 각 서비스는 Deployment/Service/ConfigMap/Secret을 기본 세트로 가지며, 이미 모든 서비스가 노출하는 `/health` 엔드포인트를 Liveness/Readiness Probe로 연결한다. 트래픽 특성상 필요한 서비스(우선 api-gateway, event-service)에는 HPA를, 외부 노출 경로에는 Ingress를, 배포 중 가용성이 중요한 서비스(payment-service 등)에는 PDB(PodDisruptionBudget)를 overlays에서 추가한다.
- 이미지 전략: `turbo prune` 기반으로 서비스별 Docker 이미지를 빌드한다. 모노레포 전체가 아니라 해당 서비스와 그 workspace 의존성만 잘라낸 컨텍스트로 빌드하여, 이미지 크기와 빌드 캐시 효율을 확보한다.
- 지금 단계에서는 `infra/k8s/` 디렉터리 구조와 README(운영 문서)만 준비한다. 실제 매니페스트 작성과 클러스터 적용은 배포 단계에서 진행한다.

## Reason

**서비스 매니페스트의 실제 변형 폭이 "값 치환" 수준이다.** 6개 서비스는 같은 모노레포에서 같은 규약(포트, `/health`, `x-request-id`, 환경 변수 주입 방식)을 따르므로, 환경 간 차이는 replica 수·리소스·이미지 태그·설정값 정도다. 이 정도 변형에 Helm의 Go 템플릿(values.yaml, `{{ }}` 문법, 조건문/반복문)을 도입하는 것은 과하다. Kustomize는 base가 그 자체로 유효한 YAML이어서 `kubectl kustomize`로 최종 결과를 바로 확인할 수 있고, "prod에서 무엇이 다른가"가 overlay 디렉터리의 패치 파일로 명시적으로 남는다. 소규모 팀이 배포 사고를 조사할 때 템플릿 렌더링 과정을 머리로 시뮬레이션할 필요가 없다는 점이 실질적인 이점이다.

**도구별 역할 분리가 운영 부담을 줄인다.** Kafka나 Prometheus를 순수 YAML이나 Kustomize로 직접 구성하는 것은 커뮤니티 차트가 이미 해결한 문제(버전 업그레이드, 기본값, CRD 관리)를 다시 푸는 일이다. 반대로 자체 서비스까지 Helm으로 감싸면 차트 버전 관리, values 스키마 유지, 릴리스 상태 관리라는 새로운 유지보수 대상이 생긴다. "우리가 만든 것은 Kustomize, 남이 만든 것은 Helm"이라는 단순한 규칙은 새 팀원에게 설명하기도 쉽고, 같은 리소스를 두 도구가 건드리는 혼선을 원천적으로 막는다.

**Probe와 PDB는 이 서비스의 트래픽 패턴에서 직접 도출된다.** 신청 오픈·매칭 발표·결제라는 순간 부하 이벤트가 명확한 서비스이므로, 롤링 업데이트가 하필 그 시점과 겹쳤을 때의 동작을 배포 구조 차원에서 보장해야 한다. `/health` 기반 Readiness Probe는 준비 안 된 파드로의 라우팅을 막고, PDB는 노드 드레인 등 자발적 중단 상황에서 최소 가용 파드 수를 지킨다. 이는 애플리케이션 코드로 해결할 수 없는, 배포 계층의 책임이다.

**turbo prune은 모노레포와 서비스별 이미지 사이의 간극을 메운다.** 6개 서비스가 packages/의 공유 패키지에 의존하므로 단순히 서비스 디렉터리만 복사해서는 빌드가 안 되고, 모노레포 전체를 이미지 컨텍스트로 쓰면 캐시가 무의미해진다. `turbo prune --docker`는 해당 서비스의 의존성 그래프만 잘라내 주므로, 공유 패키지 변경 시에만 관련 서비스 이미지가 다시 빌드된다.

**구조만 먼저 잡는 이유.** 지금 매니페스트를 전부 작성해도 검증할 클러스터 운영 경험이 없는 상태에서는 추측성 설정(리소스 값, HPA 임계치)만 쌓인다. 대신 디렉터리 구조와 규약을 README로 고정해 두면, 배포 단계에서 각 서비스 담당 작업이 같은 틀 안에서 병렬로 진행될 수 있다.

## Trade-offs

- **Kubernetes 자체의 운영 비용은 그대로 짊어진다.** 이 규모(6개 서비스, 초기 트래픽)라면 관리형 PaaS가 운영상 더 쌌을 것이다. 클러스터 버전 업그레이드, 네트워킹, 리소스 튜닝은 우리가 감당해야 하는 비용이며, 이는 학습 목표를 위해 의도적으로 받아들인 것이다.
- **Kustomize는 표현력이 낮다.** "모든 서비스에 공통 라벨과 probe 패턴을 강제한다" 같은 요구를 템플릿 한 곳에서 해결할 수 없고, base 매니페스트 6벌에 걸쳐 비슷한 YAML이 반복된다. 공통 패턴이 바뀌면 6개 파일을 함께 고쳐야 하며, 이 반복을 CI 검증(예: kubeconform, 공통 라벨 검사)으로 보완해야 한다.
- **두 도구 병행의 인지 비용.** Helm 릴리스와 Kustomize 적용 결과가 한 클러스터에 공존하므로, "이 리소스는 누가 관리하는가"를 README에 명확히 문서화하지 않으면 혼란이 생긴다. 역할 분리 원칙이 이를 줄여주지만 없애지는 못한다.
- **지금 매니페스트가 없다는 것 자체가 리스크다.** README만 있는 구조는 실제 배포 단계에서 검증되지 않은 가정(예: Secret 주입 방식, Ingress 컨트롤러 선택)을 품고 있을 수 있고, 그때 이 ADR의 세부 사항이 수정될 수 있다.
- **HPA/PDB는 선언만으로 동작하지 않는다.** HPA는 메트릭 파이프라인과 부하 테스트 기반 임계치가, PDB는 replica 2 이상이 전제다. local/dev 환경에서는 사실상 장식이 되며, prod에서만 의미를 가진다.

## Alternatives

**Helm 단독 (자체 서비스까지 차트화) — 기각.** 6개 서비스용 공통 차트 하나에 values로 서비스별 차이를 주입하는 방식은 반복을 가장 잘 제거한다. 그러나 우리 변형 폭은 값 치환 수준이라 Go 템플릿의 표현력이 필요 없고, 템플릿을 거친 YAML은 렌더링해 보기 전까지 최종 형태를 알 수 없어 디버깅 비용이 커진다. 차트/values 스키마 유지보수라는 지속 비용도 이 팀 규모에서는 이득보다 크다고 판단했다. 반복 제거의 이득보다 투명성의 손실이 크다.

**순수 YAML (도구 없이 환경별 매니페스트 전체 복사) — 기각.** 가장 단순하고 투명하지만, 3개 환경 × 6개 서비스의 매니페스트가 거의 통째로 중복된다. probe 설정 하나를 바꾸는 데 18곳을 수정해야 하고, 환경 간 의도된 차이와 실수로 생긴 차이(drift)를 구분할 수 없게 된다. 특히 결제·알림처럼 prod 설정의 정확성이 중요한 서비스에서 이 drift는 실제 사고로 이어질 수 있다.

**ECS / Cloud Run 등 관리형 컨테이너 플랫폼 — 기각.** 운영 부담만 보면 이 규모에 더 합리적인 선택일 수 있다는 점은 인정한다. 그러나 이 프로젝트는 Kubernetes 기반 마이크로서비스 운영을 직접 경험하는 것이 명시적 목표 중 하나이고, 특정 클라우드 벤더에 배포 계층이 묶이면 로컬(k8s)과 운영 환경의 구성이 달라져 local/dev/prod를 같은 매니페스트 체계로 다루는 이점을 잃는다. 표준 Kubernetes 매니페스트는 로컬 클러스터부터 어느 관리형 K8s로든 이식 가능하다는 점을 우선했다.
