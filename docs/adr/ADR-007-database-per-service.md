# ADR-007 서비스별 데이터베이스 소유 (Database per Service)

- 날짜: 2026-09-22
- 상태: Accepted

## Context

오늘사이는 오프라인 로테이션 소개팅 서비스다. 하나의 이벤트가 진행되는 동안 데이터는 성격이 다른 여러 흐름을 거친다. 회원이 프로필을 만들고, 정원이 제한된 이벤트에 동시에 신청이 몰리고, 현장에서는 라운드별 로테이션이 진행되며, 종료 후 상호 선택 결과로 매칭이 확정되고, 매칭 결과는 알림으로 전달되고, 참가비는 결제로 처리된다. 이 흐름을 따라 백엔드를 member, event, matching, notification, payment 다섯 개 서비스로 나누기로 했고(ADR에서 별도로 다룬 서비스 분리 결정), 이제 각 서비스가 데이터를 어떻게 소유할지 정해야 한다.

데이터 관점에서 각 서비스의 부하와 일관성 요구는 서로 다르다. 이벤트 신청은 정원이라는 공유 카운터를 두고 짧은 시간에 경합이 몰리는 전형적인 동시성 문제이고, 트랜잭션 격리와 잠금 전략을 이벤트 데이터에 맞춰 설계해야 한다. 매칭은 이벤트 종료 후 배치성으로 계산되며 쓰기 폭은 좁지만 읽기 조합이 많다. 알림은 발송 이력 위주의 append 성격이고, 결제는 정합성과 감사 추적이 가장 엄격하다. 이들이 하나의 스키마를 공유하면 한쪽의 마이그레이션이나 잠금이 다른 쪽에 번지고, 서비스 경계를 코드에서 아무리 나눠도 DB에서 JOIN 한 줄로 경계가 무너진다.

동시에 현실적인 제약도 있다. 지금은 환경 구성 단계이고 팀과 트래픽 모두 작다. 서비스마다 물리 DB 인스턴스를 따로 운영하는 것은 로컬 개발과 초기 운영 모두에 과한 비용이다.

## Decision

서비스별로 논리 데이터베이스를 소유한다.

- 각 서비스는 자기 전용 DB를 가진다: member_db, event_db, matching_db, notification_db, payment_db.
- 개발 환경에서는 단일 PostgreSQL 인스턴스(localhost:5432)를 공유하되, 그 안에서 다섯 개의 데이터베이스로 소유권을 구분한다. 접속 문자열은 서비스마다 자기 DB만 가리킨다.
- 타 서비스의 DB에 대한 직접 조회와 cross-database JOIN을 금지한다. 다른 서비스의 데이터가 필요하면 해당 서비스의 API를 호출하거나, 이벤트를 구독해 필요한 최소한의 사본을 자기 DB에 유지한다.
- Prisma 7 스키마와 마이그레이션은 각 서비스 디렉토리 안에 격리한다. 스키마 파일, 생성된 클라이언트, 마이그레이션 이력 모두 소유 서비스 밖에서 참조하지 않는다.
- 스키마 변경은 소유 서비스의 배포 단위로만 이루어지며, 다른 서비스는 그 변경을 API/이벤트 계약을 통해서만 관찰한다.

## Reason

첫째, 서비스 경계를 실제로 지키는 유일한 방법이기 때문이다. 공유 DB에서는 "matching이 member 테이블을 잠깐 JOIN하는" 지름길이 반드시 생기고, 한 번 생기면 스키마가 사실상 공용 API가 된다. 이후 member 서비스가 프로필 테이블을 바꾸려면 어떤 서비스가 그 테이블을 읽는지 전수 조사해야 하고, 그 시점에 서비스 분리는 이름만 남는다. DB 소유권을 물리적으로 끊어두면 경계 위반이 코드 리뷰가 아니라 연결 자체에서 막힌다.

둘째, 일관성·동시성 요구가 서비스마다 달라서다. 이벤트 신청의 정원 관리는 event_db 안에서 단일 트랜잭션으로 원자적으로 처리해야 하는 문제이고, 이 트랜잭션이 member나 payment의 테이블까지 걸치면 잠금 범위와 실패 모드가 불필요하게 커진다. 각 서비스가 자기 DB만 다루면 트랜잭션 경계가 서비스 경계와 일치하고, 신청 폭주 시의 튜닝(인덱스, 격리 수준, 잠금 전략)을 event_db에 국한해 할 수 있다.

셋째, 결제 데이터의 격리다. payment_db는 감사와 정합성 요구가 다른 데이터와 다르다. 별도 DB로 두면 접근 권한, 백업 주기, 향후 암호화 정책을 결제에만 독립적으로 적용할 수 있다.

넷째, 개발 환경의 단순함을 잃지 않는다. 단일 인스턴스 안의 논리 DB 분리는 docker-compose로 Postgres 하나만 띄우면 되므로 로컬 부담이 없다. 반면 코드가 보는 세계는 처음부터 "내 DB만 존재한다"이므로, 운영에서 인스턴스를 물리적으로 분리하더라도 접속 문자열 외에는 바꿀 것이 없다. 지금 규칙을 느슨하게 두고 나중에 분리하는 것보다, 지금 규칙을 세우고 물리 구성만 나중에 바꾸는 쪽이 훨씬 싸다.

다섯째, Prisma 스키마 격리는 이 규칙을 도구 수준에서 강제한다. 서비스 디렉토리 밖에 스키마가 없으므로 다른 서비스의 테이블에 대한 타입조차 생성되지 않고, 실수로 타 서비스 데이터를 다루는 코드는 컴파일 단계에서 걸린다.

## Trade-offs

- Cross-service 조회 비용. "이번 이벤트 참가자들의 프로필 목록"처럼 event와 member에 걸친 화면은 공유 DB라면 JOIN 한 번이지만, 이제는 API 합성(event가 참가자 ID 목록을 주고 member API로 프로필을 조회)이나 이벤트 기반 복제(필요한 프로필 필드의 사본을 event_db에 유지)로 풀어야 한다. 호출 수가 늘고, 복제를 택하면 갱신 파이프라인을 관리해야 한다. 이 비용은 실재하며, 화면마다 어느 방식을 쓸지 판단이 필요하다.
- Eventual consistency. 이벤트로 복제된 데이터는 원본과 시차가 있다. 예컨대 회원이 닉네임을 바꾼 직후 매칭 결과 화면에 옛 닉네임이 잠깐 보일 수 있다. 정원 차감이나 결제처럼 강한 일관성이 필요한 것은 단일 서비스의 트랜잭션 안에 두도록 경계를 잡았지만, 경계를 잘못 그으면 분산 트랜잭션 문제로 되돌아온다는 위험은 남는다.
- 리포팅 경로 부재. 운영 지표(이벤트별 매칭 성사율, 결제 전환율 등)는 여러 DB를 가로지르는 질의가 자연스럽지만, 이 구조에서는 불가능하다. 지금 단계에서는 필요 시 서비스 API를 조합하는 수준으로 버티고, 본격적인 리포팅은 향후 별도 경로(예: 각 DB에서 분석용 저장소로의 적재)로 해결한다. 즉 리포팅 문제를 해결한 것이 아니라 뒤로 미룬 것이다.
- 개발 환경과 운영 환경의 구성 차이. 개발은 단일 인스턴스, 운영은 분리 가능이라는 전제는 인스턴스 수준의 장애·성능 특성이 개발에서 재현되지 않음을 뜻한다.
- 초기 규모 대비 오버헤드. 지금 트래픽에서는 공유 DB로도 아무 문제가 없다. 이 결정은 현재의 편의를 미래의 경계 유지와 맞바꾼 것이며, 서비스 분리 자체가 과했다고 판명되면 이 결정의 비용도 같이 무의미해진다.

## Alternatives

- 완전 공유 DB (모든 서비스가 하나의 스키마 사용). 초기 개발이 가장 빠르고 JOIN이 자유롭다. 기각 이유: 스키마가 서비스 간 암묵적 계약이 되어 경계가 붕괴한다. 특히 신청 경합 튜닝, 결제 감사 요구, 매칭 배치 부하가 한 스키마에서 서로 간섭하게 되고, 이후 분리 비용은 시간이 갈수록 커진다. 서비스를 나눈 결정 자체를 무효화하는 선택이다.
- 단일 DB 내 스키마(namespace) 분리. PostgreSQL 스키마로 서비스별 네임스페이스만 나누는 방식. 소유권 표시는 되지만 같은 DB이므로 cross-schema JOIN이 기술적으로 가능해, 금지 규칙이 규율에만 의존하게 된다. 기각이라기보다 부분 수용: 현 개발 환경(단일 인스턴스 + 논리 DB 분리)이 사실상 이 형태의 강화판이며, 논리 DB로 나누면 JOIN이 연결 수준에서 차단되고 운영에서 인스턴스 분리로 자연스럽게 이행할 수 있어 이쪽을 택했다.
- 처음부터 서비스별 물리 인스턴스 분리. 격리는 가장 확실하지만, 로컬에서 Postgres 다섯 개를 띄우는 개발 경험과 초기 운영 비용이 현 단계의 이득을 넘어선다. 논리 분리만으로도 코드 수준의 규칙은 동일하게 강제되므로, 물리 분리는 부하가 실제로 요구할 때 접속 문자열 변경으로 이행한다.
