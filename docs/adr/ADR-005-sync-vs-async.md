# ADR-005 서비스 간 동기/비동기 통신 기준

- 날짜: 2026-09-22
- 상태: Accepted

## Context

오늘사이는 member, event, matching, notification, payment 서비스로 분리된 구조를 택했고(ADR-001 참고), 서비스가 나뉜 순간부터 "서비스끼리 어떻게 대화할 것인가"를 정해야 한다. 이 결정을 미루면 각 서비스가 임의로 REST 호출과 이벤트 발행을 섞어 쓰게 되고, 나중에 통신 방식을 정리하는 비용은 처음부터 기준을 세우는 비용보다 훨씬 크다.

이 서비스의 트래픽을 통신 관점에서 나눠 보면 성격이 뚜렷하게 다른 두 부류가 있다.

첫째, 사용자가 화면에서 결과를 기다리는 경로다. 이벤트 목록 조회, 프로필 조회, 그리고 무엇보다 정원이 있는 이벤트에 대한 참가 신청이 여기에 속한다. 20명 정원 이벤트에 신청이 몰릴 때 사용자는 "신청이 됐는지 안 됐는지"를 그 자리에서 알아야 한다. 결제 요청도 마찬가지다. 결제 버튼을 누른 사용자에게 "나중에 알려드릴게요"라고 답하는 UX는 성립하지 않는다. 이 경로의 특징은 즉각적인 성공/실패 판정이 곧 기능 요구사항이라는 점이다.

둘째, 핵심 트랜잭션이 끝난 뒤에 따라오는 후속 작업이다. 로테이션 종료 후 상호 선택 집계가 끝나 매칭이 성립하면 양쪽에게 알림을 보내야 하고, 결제가 완료되면 이벤트 참가 상태를 확정으로 갱신해야 한다. 이 작업들의 특징은 원 트랜잭션의 성패와 분리되어야 한다는 점이다. 매칭 성립이라는 사실은 알림 발송이 실패해도 유효하며, 결제 완료라는 사실은 참가 상태 갱신이 몇 초 늦어도 훼손되지 않는다.

성격이 다른 두 부류를 하나의 통신 방식으로 강제하면 어느 한쪽의 요구를 희생하게 된다. 그래서 방식을 하나로 통일하는 대신, 어떤 상황에 어떤 방식을 쓰는지 판단 기준을 명문화하기로 했다.

## Decision

통신 방식을 다음 기준으로 나눈다.

**1. 사용자 요청/응답 경로는 REST 동기 호출로 한다.**

클라이언트(web, mobile)의 요청은 api-gateway를 경유해 해당 서비스로 REST로 전달되고, 서비스는 처리 결과를 같은 요청 안에서 반환한다. 이벤트 조회, 참가 신청 확정, 결제 요청 등 사용자가 응답을 기다리는 모든 경로가 여기에 해당한다. 정원 차감처럼 동시성 제어가 필요한 판정은 해당 데이터를 소유한 서비스(event-service)가 자기 DB 트랜잭션 안에서 처리하고 즉시 성공/실패를 응답한다.

**2. 핵심 트랜잭션 커밋 이후의 후속 작업은 Kafka 이벤트로 비동기 처리한다.**

트랜잭션을 소유한 서비스가 커밋 이후 사실(fact)을 이벤트로 발행하고, 관심 있는 서비스가 구독해서 각자 처리한다. 초기 대상은 두 흐름이다.

- `match.created`: matching-service가 발행, notification-service가 구독해 알림 발송.
- `payment.completed`: payment-service가 발행, event-service가 구독해 참가 상태를 확정으로 갱신.

이벤트는 "무엇이 일어났다"는 과거형 사실만 담고, 구독자에게 특정 행동을 지시하지 않는다. 발행자는 구독자가 누구인지 몰라야 한다.

**3. 다른 서비스의 데이터가 필요하면 API 조회 또는 이벤트 구독으로 해결한다. 다른 서비스의 DB를 직접 조회하는 것은 금지한다.**

동기 경로에서 즉시 필요한 데이터는 소유 서비스의 API를 호출해서 얻고, 반복적으로 필요한 데이터는 이벤트를 구독해 자기 DB에 필요한 만큼 복제해 둔다. DB 직접 접근을 허용하는 순간 스키마가 사실상 공용 계약이 되어 서비스 분리(ADR-001, ADR-004)가 무의미해지므로 예외를 두지 않는다.

## Reason

**모든 통신을 Kafka로 하지 않는 이유.** 조회나 신청 확정까지 이벤트로 처리하면, 사용자 요청 하나가 "커맨드 발행 → 컨슈머 처리 → 결과 이벤트 발행 → 응답 대기"라는 왕복을 거쳐야 한다. 즉시 판정이 필요한 정원 차감에 이 구조를 쓰면 지연이 늘어날 뿐 아니라, 클라이언트에 결과를 돌려주기 위한 상관관계 추적(correlation) 장치를 별도로 만들어야 한다. 요청 하나의 흐름이 여러 토픽과 컨슈머에 흩어지므로 "이 신청이 왜 실패했는가"를 추적하는 디버깅 비용도 커진다. 두 명 규모의 초기 팀이 감당할 복잡도가 아니며, 얻는 것도 없다. 동기 REST는 호출 스택이 곧 인과 관계라서 x-request-id 하나로 전 구간을 따라갈 수 있다.

**모든 통신을 REST로 하지 않는 이유.** 매칭 성립 후 matching-service가 notification-service를 동기 호출한다고 하자. 알림 서비스가 다운되거나 외부 푸시 게이트웨이가 느려지면 그 장애가 매칭 확정 트랜잭션까지 거슬러 전파된다. 실제로는 매칭이 성립했는데 알림 호출 실패 때문에 매칭 처리 전체가 실패하거나 재시도되는 상황은 명백히 잘못된 결합이다. 알림은 오늘사이에서 장애 가능성이 가장 높은 부분(외부 발송 채널 의존)인데, 동기 호출로 엮으면 가장 불안정한 서비스가 가장 중요한 트랜잭션의 가용성을 결정하게 된다. payment.completed → 참가 확정도 같은 논리다. PG 응답을 받은 결제 완료 처리는 그 자체로 완결되어야 하고, event-service의 일시적 장애가 결제 완료 기록을 막아서는 안 된다. 이벤트 발행으로 분리하면 구독자 장애 시 메시지는 Kafka에 남고, 구독자가 복구된 뒤 이어서 처리된다.

**커밋 이후 발행이라는 시점을 명시한 이유.** 트랜잭션 커밋 전에 이벤트를 발행하면, 커밋이 실패했는데 알림만 나가는 유령 이벤트가 생긴다. 반대로 커밋 후 발행이 실패하면 이벤트 유실이 생긴다. 둘 중 유령 이벤트가 더 해롭다고 판단해(성립하지 않은 매칭 알림이 사용자에게 가는 것은 서비스 신뢰의 문제) 커밋 이후 발행을 원칙으로 하고, 유실 문제는 아래 Trade-offs에서 다룬다.

## Trade-offs

**최종 일관성 구간이 생긴다.** payment.completed와 참가 상태 확정 사이에는 짧은 시차가 있다. 결제 직후 참가 상태를 조회하면 아직 "확정 대기"로 보일 수 있다. 이 구간은 없앨 수 없으므로, 화면 설계가 이를 전제해야 한다(결제 완료 화면과 참가 확정 표시를 분리하는 등). 시차를 숨기려고 하지 않고 드러내는 쪽을 택한다.

**중복 처리에 대비해야 한다.** Kafka는 최소 1회 전달(at-least-once)이 현실적인 보장이므로, 컨슈머는 같은 이벤트를 두 번 받을 수 있다. 알림이 두 번 가거나 참가 확정이 두 번 갱신되지 않도록 모든 컨슈머는 이벤트 ID 기반 멱등 처리를 해야 한다. 이것은 선택이 아니라 이 구조를 택한 대가다.

**이중 쓰기(dual write) 문제가 남는다.** "DB 커밋 후 Kafka 발행"은 두 시스템에 대한 쓰기이므로, 커밋은 됐는데 발행이 실패하는 유실 가능성이 구조적으로 존재한다. 원칙적 해법은 transactional outbox 패턴이지만, 초기 단계에서는 발행 실패 로깅과 재발행 수단을 갖추는 수준으로 시작하고, 유실이 실제 운영 문제로 관측되면 outbox를 도입한다. 이 유예는 의도적인 부채이며, 그 비용을 인지하고 진다.

**두 가지 통신 패러다임을 모두 운영해야 한다.** REST 호출 체계와 Kafka 토픽/컨슈머 체계를 둘 다 유지하는 비용이 있다. 이벤트 스키마 관리, 토픽 네이밍, 컨슈머 그룹 운영 등 REST만 쓸 때는 없던 관리 대상이 생긴다. 또한 비동기 구간은 호출 스택으로 추적되지 않으므로, x-request-id를 이벤트 메타데이터에 실어 전 구간 로그를 이어 붙이는 규약을 지켜야 디버깅이 가능하다.

**경계 판단이 필요한 회색 지대가 있다.** 모든 통신이 두 부류로 깔끔하게 나뉘지는 않는다. 애매한 경우 기본 질문은 "사용자가 이 결과를 지금 기다리고 있는가"이며, 그렇다면 동기, 아니라면 비동기다. 이 질문으로도 판단이 안 되는 경우는 ADR로 남긴다.

## Alternatives

**전면 이벤트 기반(모든 통신을 Kafka로).** 서비스 간 결합을 최소화한다는 점에서 이론적으로 가장 깨끗하지만, 조회와 신청 확정 같은 요청/응답 경로에 커맨드-이벤트 왕복을 강제해 지연과 복잡도를 키운다. 특히 선착순 정원 판정처럼 즉시 응답이 기능 요구사항인 경로에서는 얻는 것 없이 잃기만 한다. 팀 규모 대비 디버깅·운영 부담도 과하다. 기각.

**전면 REST 동기 호출(Kafka 없이 시작).** 초기 구축은 가장 단순하지만, 매칭→알림, 결제→참가 확정처럼 완결된 트랜잭션 뒤의 후속 작업까지 동기로 엮으면 가장 불안정한 의존성(외부 알림 채널)이 핵심 트랜잭션의 가용성을 좌우한다. 재시도 큐를 서비스마다 자체 구현하는 식으로 보완할 수는 있으나, 그것은 결국 메시지 브로커를 어설프게 재발명하는 일이다. 기각.

**동기 호출 + 서비스별 자체 재시도 큐(브로커 없이 비동기 흉내).** 실패한 알림 호출을 로컬 테이블에 쌓고 배치로 재시도하는 방식. Kafka 운영 부담은 피할 수 있으나, 발행자가 여전히 구독자의 API를 알아야 하므로 결합도는 그대로이고, 재시도·순서·중복 처리 로직이 서비스마다 중복 구현된다. 새 구독자가 생길 때마다 발행 측 코드를 수정해야 하는 것도 이벤트 방식과의 결정적 차이다. 기각.

**서비스 간 데이터 공유를 DB 직접 조회로 해결.** 통신 자체를 줄이는 가장 손쉬운 방법이지만, 서비스별 DB 분리(ADR-004)의 전제를 무너뜨린다. 스키마 변경이 타 서비스 장애로 직결되고, 소유권 경계가 코드가 아닌 관행에 의존하게 된다. 편의를 위한 예외를 한 번 허용하면 되돌리기 어려우므로 전면 금지. 기각.
