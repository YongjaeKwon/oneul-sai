# ADR-009 인증 방식: 이메일+비밀번호(scrypt), Gateway가 검증하는 HS256 access token, 회전하는 불투명 refresh token

- 날짜: 2026-09-22
- 상태: Accepted
- 관련 설계서: [SPEC-001 회원/인증](../specs/SPEC-001-member-auth.md) (0.1절 리드 결정 기록 D1 · D4 · D5 · D6, 12절, 16절)

## Context

오늘사이의 모든 기능은 "누가" 신청하고, 입금하고, 현장에 왔는지에서 시작한다. Step 1(회원/인증)은 다른 모든 Step이 참조하는 회원 식별자의 원천을 만드는 단계이고(ADR-004), 여기서 정한 인증 방식은 이후 event · matching · payment 서비스가 호출자를 아는 방법을 그대로 결정한다. 한번 발급 구조를 정하면 토큰 형식 · 쿠키 이름 · 헤더 계약이 클라이언트와 모든 서비스에 퍼지므로 되돌리기 비싸다.

지금의 제약과 요구는 다음과 같다.

- **운영은 수동이고 규모는 작다.** 인증 수단은 이메일+비밀번호 하나다. 카카오 로그인 · 휴대폰 OTP · 온라인 본인인증(PASS 등)은 팜플렛 · 운영 메시지에 근거가 없어 결정 예정 (Step 1 이후)이다. 현장 본인 확인은 매 행사마다 신분증으로 하며, 그 기록은 참가자 · 일정 단위의 사실이라 event-service의 체크인(SPEC-005, Step 5)이 소유한다(ADR-004).
- **클라이언트는 두 개의 웹뿐이다.** 참가자 웹(`apps/web`)과 운영자 웹(`apps/admin`). 참가자 앱 로그인은 SPEC-005로 이월했다. 두 앱은 한 브라우저에 동시에 로그인될 수 있고, 참가자 웹의 XSS 한 번으로 운영자 세션을 얻는 경로가 있어서는 안 된다.
- **서비스는 Gateway 뒤에 있고, 서비스 간 호출은 아직 없다.** 외부 요청은 Gateway만 받는다. Step 1의 REST는 모두 클라이언트 → Gateway → member-service다. 다른 서비스가 회원을 알아야 하는 시점은 Step 3/5이며, 그때도 "호출자가 누구인가"는 Gateway가 넘겨 준 값으로 안다.
- **가용성이 보안만큼 중요하다.** 일요일 행사 중 운영자 계정이 잠기면 현장이 멈춘다. 이메일만 알면 누구나 남의 계정을 잠글 수 있는 구조는 받아들일 수 없다.
- **의존성과 인프라를 늘리지 않는다.** 네이티브 빌드가 필요한 라이브러리는 `pnpm-workspace.yaml`의 `allowBuilds`와 Docker 빌드 도구 체인을 늘린다(원칙 6). Redis · 키 서버 같은 새 인프라는 Step 8(운영 준비) 전에는 없다.
- **여러 탭이 동시에 뜬다.** 웹은 새로 고침 때마다 refresh를 호출해 access token을 메모리에 채운다. 탭 세 개가 동시에 부팅하면 같은 refresh token으로 요청 세 건이 거의 동시에 도착한다. 이 정상 상황이 로그아웃으로 이어지면 안 된다.

## Decision

SPEC-001이 고정한 아래 여섯 항목을 아키텍처 결정으로 채택한다. 값 · 이름 · 순서의 원천은 설계서이며 여기서는 "무엇을 왜"만 남긴다.

**1. 이메일+비밀번호, scrypt, 별도 `Credential` 테이블 없음 (D1).** 비밀번호는 `node:crypto`의 scrypt(`N = 2^17, r = 8, p = 1`, salt 16바이트, 출력 64바이트)로 해시해 `Member.passwordHash`에 직접 저장한다. 저장 형식은 `scrypt$N=...,r=...,p=...$<salt>$<hash>`로 파라미터를 문자열에 넣어 두어, 나중에 비용을 올려도 옛 해시를 검증하고 로그인 성공 시 재해시할 수 있다. 비교는 `timingSafeEqual`, 해시 전 NFKC 정규화. 두 번째 인증 수단이 도입되면 그때 `Credential` 테이블로 분리하는 마이그레이션이 정상 경로다.

**2. access token은 HS256 JWT(15분), 검증은 Gateway가 한다.** member-service가 서명하고 Gateway가 공유 시크릿 `JWT_ACCESS_SECRET`으로 검증한다(`algorithms: ['HS256']` 고정, `iss` · `aud` · `typ: 'at+jwt'` 확인, `clockTolerance` 30초). Gateway는 모든 요청에서 클라이언트가 보낸 `x-user-` 접두사 헤더를 먼저 지운 뒤, Bearer가 있고 검증에 성공했을 때만 `x-user-id` · `x-user-role`을 채우고 `Authorization`을 제거한다. Bearer가 없으면 헤더 없이 그대로 프록시한다 — 어느 경로가 인증을 요구하는지는 서비스의 `@Public()` 데코레이터가 원천이며 Gateway는 경로별 인증 정책과 역할 규칙을 갖지 않는다.

**3. 내부 토큰으로 서비스가 Gateway를 신뢰한다.** Gateway는 프록시하는 모든 요청에 `x-internal-token`(env `INTERNAL_API_TOKEN`, 두 앱이 같은 값)을 붙이고, 서비스의 전역 가드는 이 값을 `timingSafeEqual`로 가장 먼저 확인한다(`/health` · `/docs` 제외). 서비스는 `Authorization`을 보지 않고 내부 헤더만 본다. 이로써 Gateway의 책임은 ADR-004의 "라우팅 · request-id · 로깅 · 에러 정책"에 **토큰 검증 · 내부 헤더 · 내부 토큰 부착 · IP rate limit · `POST /api/v1/auth/*`의 `Origin` 허용 목록 확인**이 더해진다. 비즈니스 로직 금지는 그대로다.

**4. refresh token은 불투명 랜덤 · 해시 저장 · 회전 · 유예 창 · 재사용 탐지 (D5).** 32바이트 랜덤 토큰을 발급하고 DB에는 SHA-256 해시만 둔다(30일, 가족 절대 수명 90일). refresh마다 옛 토큰을 `ROTATED`로 바꾸고 같은 `familyId`로 새 토큰을 발급하며, 이 판정 · 회전은 `SELECT ... FOR UPDATE` 한 트랜잭션에서 직렬화한다. 회전 직후 60초 안에 옛 토큰이 다시 오면 다중 탭 경합으로 보고 access token만 새로 준다(유예) — 단, 같은 가족에 `ACTIVE` 토큰이 남아 있을 때만이다. 가족이 이미 폐기됐으면 60초 안이라도 거부해, 로그아웃 · 비밀번호 변경 직후 옛 토큰으로 새 access token을 받는 창을 두지 않는다. 유예 창 밖의 `ROTATED` 제시는 탈취 신호로 보고 가족 전체를 `REVOKED(REUSE)`로 끊는다.

**5. 웹 저장은 앱별로 나뉜 httpOnly 쿠키 (D4).** access token은 브라우저 메모리, refresh token은 Gateway 호스트의 `HttpOnly; Secure; Path=/api/v1/auth` 쿠키다. 참가자 웹은 `onulsai_rt_web`(`SameSite=Lax`), 운영자 웹은 `onulsai_rt_admin`(`SameSite=Strict` + `Origin` 확인). **어느 쿠키를 읽을지는 요청이 정한다** — refresh · logout 요청은 본문에 `client`(`WEB` | `ADMIN`)를 싣고, 서비스는 그 클라이언트의 쿠키 하나만 읽는다. 두 쿠키가 한 브라우저에 함께 있는 것(web과 admin에 동시에 로그인)은 정상이며 에러가 아니다. `client = ADMIN`이면 login · refresh · logout 모두에서 `Origin = ADMIN_ORIGIN`을 추가로 확인한다. 토큰 행에 발급 앱(`client`)을 저장하고 요청의 `client`와 다르면 거부한다. 로그인 CSRF(다른 사이트의 form이 공격자 세션 쿠키를 심는 것)는 본문 경로에 `Content-Type: application/json`을 요구하고 Gateway가 `Origin`을 허용 목록과 대조해 막는다. 보호된 데이터는 모두 클라이언트 컴포넌트에서 조회하며 Next 서버 컴포넌트 · Route Handler는 Gateway를 호출하지 않는다 — BFF는 두지 않는다. _(2026-09-23 설명) 이 문장의 호출 금지는 토큰이 필요한 보호 데이터에 대한 것이다. 토큰 없이 부르는 `@Public` 조회를 서버 컴포넌트가 부르는 것은 BFF가 아니다 — [SPEC-002](../specs/SPEC-002-meetup-schedule.md) D11, [`docs/api/README.md`](../api/README.md) 5.5절._

**6. 계정 잠금 대신 계정 단위 지수 백오프, IP 제한은 Gateway 인메모리 (D6).** 15분 창 안에 비밀번호 확인 실패가 4회 쌓이면 그 계정의 다음 확인(k번째 시도, k ≥ 5)은 `min(2^(k−5), 30)`초 뒤에 시작한다. **지연은 검증 앞에 오고, 같은 계정의 시도는 직렬화된다**: `LoginBackoffService`가 인메모리 `Map<memberId, Promise<void>>` 체인으로 같은 계정의 "지연 → scrypt 검증 → 카운터 갱신"을 순서대로 실행한다. 지연은 `setTimeout` 대기라 트랜잭션 · DB 커넥션을 잡지 않으며, 카운터 갱신은 UPDATE 한 문장(`CASE`로 창 판정, `RETURNING`)이다. 성공 · 실패 · 정지 여부와 무관하게 지연이 먼저다. 없는 이메일은 더미 해시로 검증 한 번을 돈다. 잠금 상태 · 423 응답 · 잠금 해제 API는 없다. ADMIN · MEMBER 동일. 같은 계정에 대한 병렬 추측은 체인 뒤에 줄을 서므로 백오프를 우회하지 못하고, 여러 계정 · 없는 이메일에 걸친 처리량은 Gateway의 IP 단위 인메모리 토큰 버킷(로그인 · 가입 · refresh와 비밀번호를 확인하는 회원 경로, 분당 `RATE_LIMIT_AUTH_PER_MINUTE`)과 scrypt 동시 실행 · 대기 큐 상한이 제한한다. 체인은 IP 버킷과 같은 단일 인스턴스 범위다.

## Reason

**검증을 Gateway에 두는 이유.** 모든 외부 요청이 Gateway를 지나므로 검증 지점이 하나면 시크릿을 아는 곳도 하나(발급자 외)다. 서비스는 `x-user-id` · `x-user-role`만 보면 되므로 Step 3/5에서 event-service가 생겨도 JWT 라이브러리 · 시크릿 · 검증 코드를 서비스마다 반복하지 않는다. 다만 "헤더를 믿는다"는 것은 "헤더를 위조할 수 있으면 누구든 된다"는 뜻이라, 두 겹으로 막는다: Gateway가 들어온 `x-user-*`를 접두사로 전부 지워 외부 위조를 막고(이름을 열거하지 않으므로 내부 헤더가 늘어도 목록을 빠뜨릴 수 없다), 내부 토큰으로 "서비스 포트에 도달했다"를 "비밀을 알고 있다"로 올린다. 네트워크 격리(Step 8, `ClusterIP`) 전까지 서비스 포트를 외부에 열지 않는 규칙은 그대로다. Gateway가 경로별 인증 정책을 갖지 않는 것은 Step 2에서 공개 일정 조회가 생겨도 Gateway PR이 필요 없게 하려는 것이다 — 인증 요구는 그 엔드포인트를 소유한 서비스가 안다.

**HS256을 먼저 쓰는 이유.** 검증자가 Gateway 하나인 동안 비대칭 키가 주는 것은 "검증자에게 서명 능력을 주지 않는다"는 이점뿐인데, 그 검증자가 우리 Gateway다. 키 쌍 생성 · JWKS 엔드포인트 · 키 회전 절차는 지금 없는 문제를 위한 비용이다. `alg` 혼동 공격은 `algorithms: ['HS256']`을 고정해 막는다. 전환 조건이 오면 발급 측을 RS256으로 바꾸고 Gateway가 JWKS를 읽게 하면 되며, refresh token은 DB 기반이라 영향이 없다.

**scrypt를 쓰는 이유.** bcrypt · argon2는 네이티브 빌드가 필요해 `allowBuilds`와 Docker 이미지 빌드 도구 체인이 늘어난다. scrypt는 `node:crypto`에 있고 메모리 하드 함수라 GPU 공격에 bcrypt보다 강하며, OWASP Password Storage Cheat Sheet가 argon2id 다음 순위로 권고한다. 파라미터를 저장 형식에 넣어 두는 것은 "나중에 올릴 때 옛 해시를 어떻게 검증하는가"를 지금 결정해 두는 가장 싼 방법이다. 비용(호출당 약 128MiB · 100ms 이상)이 libuv 스레드풀을 포화시킬 수 있다는 점은 Gateway IP 제한 · 동시 실행 상한 · 대기 큐로 세 겹으로 막는다.

**`Credential` 테이블을 두지 않는 이유.** 분리의 유일한 근거가 "결정 예정"인 두 번째 provider였다. 지금은 1:1이라 관계 · 가입 트랜잭션 · 응답 중첩이 모두 불필요하고, 필요해지는 시점의 마이그레이션은 하위 호환 변경이다(원칙 6).

**refresh 회전과 유예 창을 같이 두는 이유.** 회전 없이 만료 · 폐기까지만 두는 안은 코드가 훨씬 단순하지만, 탈취된 refresh token이 재사용되는 것을 잡을 수단이 없다. 회전만 두고 유예 창이 없으면 세 탭이 동시에 부팅하는 정상 상황이 재사용 탐지로 오인돼 로그아웃된다. "부팅 경합은 초 단위, 탈취 재사용은 분 단위"라는 가정 아래 60초 유예 창이 둘을 가른다. `FOR UPDATE` 직렬화는 "영향 행 0"처럼 타이밍에 의존하는 경로를 없애기 위해서다.

**쿠키를 앱별로 나누는 이유.** httpOnly 쿠키의 이점은 세션을 밖으로 들고 나갈 수 없다는 것이다. 그러나 페이지에 실행된 XSS는 쿠키를 못 읽어도 `credentials: 'include'`로 refresh를 계속 호출할 수 있다. 두 앱의 쿠키 이름이 다르고 토큰 행이 발급 앱을 기억하므로, 참가자 웹의 XSS가 운영자 쿠키로 refresh해도 `client` 불일치로 거부된다. 운영자 쿠키에 `SameSite=Strict`와 `Origin` 확인을 더한 것도 같은 이유다 — 참가자 웹에서 실행된 스크립트가 `client: ADMIN`으로 바꿔 부르면 쿠키는 실리지만(같은 사이트) `Origin`이 참가자 웹이라 거부된다. 읽을 쿠키를 "브라우저에 있는 쿠키"가 아니라 요청 본문의 `client`로 정하는 것은, 두 앱에 동시에 로그인한 브라우저(쿠키 두 개 공존)가 정상 상황이기 때문이다. 있는 쿠키로 판정하면 이 상황을 에러로 만들거나, 둘 중 하나를 임의로 고르게 된다. 이 방식의 조건은 웹과 Gateway가 같은 사이트여야 한다는 것이며, 그래서 BFF 여부를 프로덕션 도메인 결정(Step 8)에 묶었다.

**잠금 대신 백오프인 이유.** 계정 잠금은 이메일만 알면 누구나 그 계정을 잠글 수 있는 가용성 공격 벡터다 — 행사 당일 운영자 계정을 포함해서. 백오프는 정상 사용자를 막지 않고(느려질 뿐) 잠금 해제 API · 화면 · 423 응답이 필요 없다. ADMIN을 예외로 두면 운영자 계정이 무제한 추측에 노출되므로 예외가 없다.

**지연을 검증 앞에 두고 계정 단위로 직렬화하는 이유.** 지연을 실패 응답 뒤에만 두면 두 가지가 새어 나간다. 첫째, 공격자는 응답을 기다릴 필요가 없다 — 같은 계정에 요청을 병렬로 보내면 각 요청은 지연 없이 검증까지 도달하고, 지연은 이미 검증이 끝난 응답을 늦출 뿐이라 추측 속도를 제한하지 못한다. 둘째, 성공은 즉시 200이므로 응답이 빨리 오지 않으면 "틀림"으로 판정하고 요청을 끊을 수 있어 지연 자체가 타이밍 오라클이 된다. 같은 계정의 확인을 인메모리 체인으로 직렬화하고 지연을 검증 앞에 두면, k번째 시도는 앞선 k−1번이 끝나고 지연이 지난 뒤에야 검증에 도달하므로 병렬로 보내도 한 계정의 추측 속도는 순차와 같고(30초 상한 기준 시간당 120회 안팎), 맞는 비밀번호도 같은 시간을 기다리므로 응답 시간이 정오를 드러내지 않는다. 직렬화를 DB 행 잠금(`FOR UPDATE`)이 아니라 인메모리 체인으로 하는 것은, 최대 30초의 대기 동안 DB 커넥션을 잡으면 공격받는 계정 수만큼 커넥션 풀이 비어 모든 요청이 멈추기 때문이다 — 잠금을 없앤 이유(가용성)를 다른 경로로 되살리지 않는다. 단일 인스턴스 전제는 IP 버킷과 같고 Step 8에서 함께 다룬다. 없는 이메일도 더미 해시 검증을 지나므로 scrypt 비용 차이로 존재 여부가 새지 않는다. 여러 계정에 걸친 병렬 처리량은 백오프가 아니라 IP 제한과 scrypt 큐가 제한한다 — 두 장치의 역할을 섞지 않는다.

**IP 제한을 인메모리로 시작하는 이유.** Gateway가 단일 인스턴스인 동안 Redis는 없는 문제를 위한 인프라다. 전환 조건(다중 인스턴스)은 ADR-008의 HPA와 정확히 같은 시점이라 Step 8에서 함께 다룬다.

**온라인 본인인증을 넣지 않는 이유.** 팜플렛 · 운영 메시지의 본인 확인은 "행사 당일 신분증"이다. 이는 참가자 · 일정 단위의 사실이므로 회원 단위의 영구 "확인 완료" 플래그는 근거가 없는 제품 사실이고, "확인됐는가"의 진실이 두 DB에 생기는 것을 막기 위해 event-service의 체크인에만 둔다(D2, ADR-004).

## Trade-offs

- **공유 시크릿의 반경.** `JWT_ACCESS_SECRET`을 아는 곳(member-service, Gateway) 어디서든 유효한 access token을 만들 수 있다. 교체는 두 앱에 동시 배포이며, 그 순간 기존 access token은 전부 무효(최대 15분)가 되고 클라이언트가 refresh로 복구한다. 검증자가 늘면 이 반경이 그대로 늘어난다 — 그것이 RS256 전환 조건이다.
- **헤더 신뢰 모델은 네트워크 규칙에 기댄다.** 내부 토큰은 두 번째 장치일 뿐, 서비스 포트가 외부에 열리고 토큰까지 새면 막을 수 없다. 프로덕션에서 `INTERNAL_TOKEN_INVALID`가 한 건이라도 보이면 Gateway 우회 또는 설정 오류로 보고 경보한다.
- **로그아웃 · 정지 · 탈퇴가 access token에 즉시 반영되지 않는다.** 거부 목록이 없으므로 남은 access token은 만료까지 Gateway를 통과한다. 회원 API가 상태를 읽어 `SUSPENDED` · `WITHDRAWN`을 거부하지만 "로그아웃했다"는 사실은 알지 못한다. 15분을 받아들인다.
- **유예 창은 탐지를 늦춘다.** 공격자가 정상 클라이언트보다 먼저 회전시키면, 정상 클라이언트의 다음 refresh(최대 access 수명 뒤)에서야 가족이 폐기된다. 탐지 지연 최대 "access 수명 + 유예 창"이 유예 창의 비용이다. 60초는 가정이며 `auth.refresh.grace_hit` 관측 후 Step 8에서 조정한다.
- **회전은 코드와 테스트를 늘린다.** `familyId` · `ROTATED` · `FOR UPDATE` · 유예 판정 · 동시 refresh 통합 테스트가 모두 이 결정의 비용이다. 실제 Postgres 위의 통합 테스트를 CI에 붙인 이유이기도 하다.
- **배포 제약.** 쿠키 방식은 웹과 Gateway가 같은 사이트여야 한다. 프로덕션 도메인이 이를 만족하지 못하면 BFF 또는 도메인 재조정이 필요하고, Safari는 `http://localhost`에서 `Secure` 쿠키를 허용하지 않아 로컬은 `COOKIE_SECURE=false`가 필요하다.
- **백오프 대기 중인 요청은 서비스 메모리에 쌓인다.** 지연이 `setTimeout`이라 스레드 · 커넥션은 잡지 않지만, 대기 중인 요청과 계정별 체인 항목은 프로세스 메모리에 남는다. 지연은 4회 이상 실패한 실존 계정의 다음 시도에만 걸리고, 그 계정에 쌓이는 요청 수는 IP 제한이 누른다. 체인이 비면 항목을 지운다.
- **백오프는 계정 존재를 드러낸다.** 4회 이상 실패한 계정의 다음 시도만 느려지므로, 없는 이메일과 구분된다 — 없는 이메일에는 카운터가 없다. scrypt 비용은 더미 검증으로 맞추므로 새는 것은 이 지연뿐이다. 잠금(423)이 드러내던 것과 같은 정보이며, 대신 가용성 공격이 되지 않는다. 가입 409도 이메일 존재를 드러낸다 — 이메일 인증 발송(Step 7) 없이는 피할 수 없다.
- **IP 제한과 계정 직렬화는 단일 인스턴스 전제다.** 다중 인스턴스가 되는 순간 IP 버킷도 계정 체인도 인스턴스마다 따로 세어져 제한이 느슨해진다. Step 8 전에 Gateway · member-service를 여러 개 띄우지 않는다는 운영 규칙에 기댄다.
- **scrypt는 스레드풀을 점유한다.** 인증 없는 로그인 요청만으로 모든 인증 경로를 느리게 만들 수 있어 세 겹의 방어(IP 제한, 동시 실행 상한, 대기 큐)와 `UV_THREADPOOL_SIZE` 권고가 따라온다. 파라미터를 낮추는 것으로는 해결되지 않는다.
- **`Credential` 분리를 미룬 비용.** 두 번째 인증 수단이 도입되면 `passwordHash` · 실패 카운터를 옮기는 마이그레이션과 가입 트랜잭션 변경이 그때 필요하다. 하위 호환 변경이라 받아들인다.

## Alternatives

**서비스가 각자 JWT를 검증(Gateway는 passthrough) — 기각.** Gateway를 순수 프록시로 두고 각 서비스가 시크릿을 갖고 검증하는 안. Gateway가 얇아지고 Gateway 우회 시에도 안전하다는 장점이 있다. 그러나 시크릿을 아는 곳이 서비스 수만큼 늘어나 공유 시크릿의 반경이 커지고, 서비스마다 검증 코드 · 라이브러리 · 예외 처리가 반복되며, Step 3/5에서 서비스가 늘 때마다 같은 것을 다시 만든다. 검증을 한 곳에 두고 헤더 계약으로 넘기는 편이 서비스를 얇게 유지한다. 우회 위험은 내부 토큰과 네트워크 규칙으로 막는다.

**RS256/JWKS를 처음부터 — 보류(Step 8).** 검증자에게 서명 능력을 주지 않고 키 회전이 깔끔하다. 그러나 검증자가 Gateway 하나인 동안 얻는 것이 없고, 키 쌍 관리 · JWKS 엔드포인트 · 회전 절차가 지금 없는 문제를 위한 비용이다. 전환 조건을 위 표에 적어 두었다.

**refresh 회전 없음(만료 · 폐기만) — 기각(D5).** `familyId` · `ROTATED` · 유예 창 · 재사용 탐지 · 동시 refresh 테스트가 사라져 훨씬 단순하다. httpOnly 쿠키가 XSS 탈취를 이미 막으므로 남는 위협은 기기 · 네트워크 탈취뿐이라는 논거였다. 채택하지 않은 이유는 탈취 재사용을 잡는 유일한 수단이 회전이고, 유예 창이 다중 탭 위험을 흡수하므로 지금 넣는 비용이 작기 때문이다.

**localStorage 토큰 저장 — 기각(D4).** 구현이 단순하고 탭 간 공유가 쉬우며 웹과 Gateway가 다른 사이트여도 된다. 그러나 XSS 한 번에 refresh token까지 반출된다. 대신 같은 사이트여야 한다는 배포 제약을 받아들였다.

**BFF(Next 서버가 세션을 들고 Gateway를 대신 호출) — 보류(Step 8).** SSR 인증이 자연스럽고 토큰이 브라우저에 아예 없다. 그러나 Next 서버에 세션 저장소와 프록시 계층이 생기고, 두 앱 각각에 그 계층이 필요하며, Step 1의 화면은 모두 클라이언트 조회로 충분하다. 프로덕션 도메인 결정이 SSR 인증을 요구할 때 다시 본다.

**bcrypt · argon2 — 기각.** 네이티브 빌드가 필요해 `allowBuilds`와 Docker 빌드 도구 체인이 늘어난다. scrypt(`node:crypto`)로 충분하다.

**계정 잠금(5회/15분) + ADMIN 예외, 또는 (계정, IP) 조합 카운터 — 기각(D6).** 잠금은 가용성 공격 벡터이고 ADMIN 예외는 운영자 계정을 무제한 추측에 노출한다. (계정, IP) 조합은 IP를 바꾸는 공격자에게 무력하고 저장 구조가 커진다. 지수 백오프로 대체했다.

**실패 응답만 늦추는 백오프(검증 뒤 지연, 직렬화 없음) — 기각.** 설계서 초안의 방식이다. 구현이 가장 단순하지만, 응답을 기다리지 않는 병렬 요청이 지연을 그대로 우회하고, 성공이 즉시 응답하므로 지연 유무가 정오와 실패 횟수를 타이밍으로 드러낸다(보안 리뷰). 검증 앞 지연 + 계정 단위 인메모리 직렬화로 바꿨다(테이블 · API 변경 없음).

**회원 행 `FOR UPDATE`로 백오프를 직렬화 — 기각.** 다중 인스턴스에서도 직렬화가 유지된다는 장점이 있지만, 최대 30초의 대기 동안 DB 커넥션을 잡으므로 공격받는 계정 몇 개만으로 커넥션 풀이 비어 서비스 전체가 멈춘다 — 잠금을 없앤 이유(가용성)를 되살린다. 트랜잭션 제한 시간도 최대 지연 이상으로 늘려야 한다. 단일 인스턴스 동안은 인메모리 체인으로 충분하고, 다중 인스턴스 대응은 분산 rate limit과 함께 Step 8에서 본다.

**브라우저에 있는 쿠키로 클라이언트를 판정 — 기각.** refresh · logout에서 `onulsai_rt_web` · `onulsai_rt_admin` 중 있는 쪽을 쓰고 둘 다 있으면 400으로 거부하는 안. 본문 필드가 하나 줄지만, web과 admin에 동시에 로그인한 정상 브라우저가 어느 쪽도 refresh하지 못하게 된다. 요청 본문의 `client`로 읽을 쿠키를 정하고 나머지 쿠키는 무시한다.

**Redis 기반 분산 rate limit을 처음부터 — 보류(Step 8).** 단일 인스턴스 동안은 없는 문제를 위한 인프라이며, 전환 시점이 ADR-008의 HPA 도입과 같다.

**`Credential` 테이블을 미리 분리 — 기각(D1).** 두 번째 provider가 결정 예정인 동안 관계 · 트랜잭션 · 응답 중첩을 늘릴 이유가 없다. 지금 요구에 없는 확장 포인트를 만들지 않는다(CLAUDE.md 원칙 6).

**온라인 본인인증(PASS 등)을 Step 1에 포함 — 기각(D2).** 팜플렛 · 운영 메시지의 본인 확인은 현장 신분증이며, 회원 단위 확인 플래그는 근거 없는 제품 사실이다. 현장 확인 기록은 event-service의 체크인(SPEC-005)이 소유한다.
