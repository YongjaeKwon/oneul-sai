# ADR-002 백엔드 프레임워크로 NestJS를 채택한다

- 날짜: 2026-09-22
- 상태: Accepted

## Context

오늘 사이는 오프라인 로테이션 소개팅 서비스다. 백엔드가 감당해야 할 도메인을 실제 흐름 기준으로 나열하면 다음과 같다.

- **이벤트 정원과 동시 신청**: 이벤트마다 성비·정원이 정해져 있고, 인기 이벤트는 오픈 직후 신청이 몰린다. 정원 초과 방지, 대기열, 신청 취소에 따른 승계 같은 로직이 이벤트 도메인 안에서 상태 전이로 관리되어야 한다.
- **현장 로테이션 진행**: 행사 당일 라운드 테이블 배정을 계산하고, 운영자가 라운드를 넘기면 참가자에게 다음 자리를 안내해야 한다. 배정 알고리즘과 진행 상태 관리가 한 서비스 안에서도 뚜렷하게 분리되는 하위 도메인이다.
- **매칭과 알림**: 행사 종료 후 참가자의 상호 선택을 집계해 매칭을 확정하고, 결과를 알림으로 전달한다. 매칭 확정과 알림 발송은 서로 다른 서비스의 책임이며, 그 사이는 결국 이벤트(메시지) 기반으로 이어져야 한다.
- **결제**: 참가비 결제와 취소·환불 규정 처리는 외부 PG 연동과 멱등성 보장이 핵심이고, 장애 시 다른 도메인과 격리되어야 한다.

이를 반영해 member, event, matching, notification, payment 다섯 개 서비스와 api-gateway로 백엔드를 나누기로 했다(서비스 분리 자체의 결정은 별도 ADR에서 다룬다). 이 ADR은 그 서비스들을 **무엇으로 만들 것인가**에 대한 결정이다.

전제 조건은 다음과 같다. 프론트엔드(web, admin, mobile)는 모두 TypeScript이고, 모노레포에서 스키마·타입을 공유할 계획이다. 팀 규모는 작고, 초기에는 한 사람이 여러 서비스를 오가며 작업한다. 지금 단계는 헬스체크와 배선(wiring)까지만 만드는 환경 구축기이지만, 프레임워크 선택은 이후 되돌리기 가장 비싼 결정 중 하나이므로 지금 확정한다.

## Decision

백엔드 다섯 개 서비스와 api-gateway를 모두 **NestJS 12**로 작성한다. HTTP 계층은 기본 어댑터인 **Express 5**를 사용하고, 모듈 시스템은 모노레포 컨벤션에 맞춰 **ESM**(`"type": "module"`, NodeNext)으로 통일한다. API 문서는 `@nestjs/swagger`로 코드에서 생성한다.

## Reason

**1. 모듈/DI 구조가 서비스 내부의 도메인 분리에 맞는다.** 서비스를 다섯 개로 나눴다고 해서 각 서비스 내부가 단순해지는 것은 아니다. 예를 들어 event-service 하나만 봐도 이벤트 CRUD, 정원·신청 관리, 현장 로테이션 진행이라는 성격이 다른 하위 도메인이 공존한다. NestJS의 모듈 단위(`EventModule`, `RegistrationModule`, `RotationModule` 같은 식)는 이 경계를 코드 구조로 강제할 수 있는 가장 저렴한 수단이다. DI 컨테이너 덕분에 정원 검증 로직이나 배정 알고리즘을 프로바이더로 분리해 `@nestjs/testing`으로 단위 테스트하기도 쉽다. 동시 신청·매칭 집계처럼 버그가 곧 고객 클레임이 되는 로직일수록 테스트 가능성이 중요하다.

**2. 서비스 다섯 개에 같은 뼈대를 복제할 수 있다.** Express를 그대로 쓰면 서비스마다 라우팅 구성, 에러 처리, 검증, 설정 로딩 방식이 미묘하게 달라지는 것을 사람이 리뷰로 막아야 한다. NestJS는 컨트롤러/프로바이더/모듈, 파이프/필터/인터셉터라는 규약을 프레임워크 차원에서 제공하므로, member-service에서 잡은 구조를 payment-service에 그대로 옮길 수 있다. 작은 팀이 여러 서비스를 오가며 작업하는 상황에서 "어느 서비스를 열어도 같은 모양"이라는 것 자체가 생산성이다.

**3. Swagger 통합.** 게이트웨이 뒤의 서비스가 다섯 개면 API 문서가 코드와 어긋나는 순간 통합 비용이 바로 발생한다. `@nestjs/swagger`는 데코레이터 기반으로 OpenAPI 문서를 코드에서 생성하므로 문서가 낡는 속도가 훨씬 느리고, 프론트엔드(web/admin/mobile) 쪽에서 계약을 확인하는 기준점이 된다.

**4. 전 스택 TypeScript 통일.** 프론트가 전부 TypeScript인 상황에서 백엔드까지 TypeScript면 언어 컨텍스트 스위칭이 없고, 모노레포의 공유 패키지(zod 스키마, 공통 타입)를 서버·클라이언트가 그대로 나눠 쓸 수 있다. 신청 요청의 검증 스키마를 한 번 정의해 양쪽에서 쓰는 식의 이득은 도메인 모델이 자주 바뀌는 초기에 특히 크다.

**5. 메시징으로의 확장 여지.** 매칭 확정 → 알림 발송, 결제 완료 → 신청 확정 같은 흐름은 장기적으로 동기 HTTP보다 이벤트 기반이 맞다. NestJS는 `@nestjs/microservices`로 Kafka 등의 consumer를 같은 모듈/DI 모델 안에서 붙일 수 있으므로, 지금 HTTP로 시작해도 나중에 notification-service에 Kafka consumer를 추가할 때 프레임워크를 바꾸거나 구조를 새로 잡을 필요가 없다. 이것은 "지금 Kafka를 도입한다"는 결정이 아니라, 도입 시점에 갈아탈 비용이 없도록 미리 문을 열어 두는 결정이다.

**6. Express 5 기반.** 어댑터로 Fastify도 선택할 수 있으나 기본값인 Express를 쓴다. 우리 트래픽 특성상(이벤트 오픈 순간의 스파이크는 있지만 절대량은 크지 않다) HTTP 프레임워크 처리량이 병목이 될 가능성은 낮고, Express 생태계의 미들웨어 호환성과 자료 축적이 초기 개발 속도에 더 유리하다. 병목이 실측되면 어댑터 교체는 NestJS 안에서 상대적으로 국소적인 변경이다.

## Trade-offs

솔직하게 지불하는 비용은 다음과 같다.

- **추상화 비용과 학습 곡선.** DI, 데코레이터, 모듈 스코프, 라이프사이클 훅은 Express만 쓰던 사람에게 초기 진입 장벽이다. 헬스체크 하나 만드는 데도 모듈·컨트롤러·부트스트랩 보일러플레이트가 붙는다. 지금 단계(환경 구축)에서는 체감상 과한 구조로 보일 수 있고, 그 비용을 도메인 로직이 들어오는 시점의 이득으로 상환한다는 베팅이다.
- **데코레이터/메타데이터 의존.** `reflect-metadata`와 `experimentalDecorators`에 기대는 구조라 TC39 표준 데코레이터와의 간극이 있고, tsconfig 옵션(`emitDecoratorMetadata` 등)이 서비스 전반의 전제 조건이 된다. 이를 공유 프리셋(`@oneul-sai/typescript-config/nestjs.json`)으로 묶어 관리 비용을 낮추지만, 의존 자체가 사라지는 것은 아니다.
- **ESM 조합의 마찰.** NestJS 생태계의 문서·예제 다수가 여전히 CJS 전제라, ESM + NodeNext 조합에서는 상대 경로 import에 `.js` 확장자를 붙이는 규칙이나 일부 라이브러리의 호환 문제를 우리가 직접 해결해야 하는 경우가 있다.
- **런타임 성능 상한.** Node.js + Express라는 선택은 Go 같은 대안 대비 단일 인스턴스 처리량과 CPU 바운드 작업(예: 라운드 배정 계산이 커질 경우)에서 불리하다. 우리 규모에서 문제가 될 가능성은 낮다고 판단하지만, 이것은 측정으로 검증해야 할 가정이지 사실이 아니다.
- **프레임워크 종속.** 요청 파이프라인의 상당 부분이 NestJS 규약 위에 놓이므로, 훗날 탈출 비용은 Express 단독 구성보다 크다.

## Alternatives

**Express / Fastify 단독 (프레임워크 없이 직접 구성)** — 기각. 진입 장벽이 없고 가장 가볍지만, 구조 규약이 없다. 다섯 개 서비스의 계층 구조·검증·에러 처리·DI(혹은 그 부재)를 전부 자체 컨벤션으로 정의하고 문서화하고 리뷰로 지켜야 하는데, 그것은 사실상 사내 프레임워크를 만드는 일이다. 작은 팀이 그 비용을 지불하면서 얻는 것이 "유연함"뿐이라면 남는 장사가 아니라고 판단했다. Fastify의 성능 이점은 매력적이나 위에서 언급했듯 우리 병목이 아니며, 필요해지면 NestJS 어댑터 교체로 흡수할 수 있다.

**Spring Boot (Java/Kotlin)** — 기각. 도메인 분리, DI, 생태계 성숙도 면에서 가장 검증된 선택지이고 결제·트랜잭션 처리 레퍼런스도 풍부하다. 그러나 프론트엔드 전부가 TypeScript인 팀에서 백엔드만 JVM으로 가면 언어·빌드·배포 스택이 이원화되고, 모노레포에서의 타입 공유가 끊기며, 초기의 작은 팀이 두 생태계를 동시에 유지해야 한다. 팀 스택 분리 비용이 Spring이 주는 이득을 상회한다고 판단했다.

**Go (chi/echo 등)** — 기각. 런타임 효율, 배포 용이성(단일 바이너리), 동시성 모델은 분명한 장점이고, 트래픽이 커지면 게이트웨이나 특정 서비스에 한해 재검토할 가치가 있다. 그러나 현재 팀의 주력 언어가 아니어서 생산성 손실이 즉시 발생하고, 웹 도메인 생태계(검증, ORM, Swagger 연동 등)에서 조립 비용이 크며, 프론트와의 타입 공유도 포기해야 한다. 지금 필요한 것은 도메인을 빠르게 굳히는 것이지 런타임 효율이 아니다.

이 결정은 참가자 수·이벤트 동시성이 현재 가정을 크게 벗어나 성능 문제가 실측되는 시점에 서비스 단위로 재검토한다.
