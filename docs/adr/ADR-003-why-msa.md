# ADR-003 처음부터 6개 서비스로 제한된 MSA를 채택한다

- 날짜: 2026-09-22
- 상태: Accepted

## Context

오늘사이는 오프라인 로테이션 소개팅 서비스다. 시스템 관점에서 이 도메인은 성격이 뚜렷하게 다른 여러 흐름으로 나뉜다.

첫째, **이벤트 신청 흐름**이다. 이벤트는 정원이 정해져 있고(예: 남녀 각 8명), 모집 오픈 직후 짧은 시간에 신청이 몰린다. 정원 초과 없이 동시 신청을 처리해야 하므로, 이 구간은 트래픽이 순간적으로 튀고 데이터 정합성 요구가 강하다.

둘째, **현장 로테이션 진행 흐름**이다. 이벤트 당일 현장에서 라운드가 돌아가는 동안 참가자와 진행자가 시스템을 실시간으로 사용한다. 이 구간에서 가장 중요한 것은 가용성이다. 결제 모듈이나 알림 발송이 무슨 문제를 겪고 있든, 현장에서 진행 중인 로테이션은 멈추면 안 된다. 오프라인 행사는 재시도가 불가능하기 때문이다.

셋째, **매칭과 알림 흐름**이다. 로테이션 종료 후 참가자들의 선택을 수집해 매칭 결과를 계산하고, 결과를 알림으로 전달한다. 알림은 외부 채널(푸시, 메시지)에 의존하므로 외부 장애에 노출되어 있고, 지연은 허용되지만 유실은 곤란하다.

넷째, **결제 흐름**이다. 참가비 결제는 외부 PG에 의존하며, 금전과 개인 결제 정보를 다루므로 다른 어떤 영역보다 보안 요구가 높다.

여기에 회원(가입, 프로필, 인증)이라는 기반 도메인이 있다. 이렇게 도메인 경계가 비교적 명확하고, 각 경계마다 부하 패턴·가용성 요구·보안 요구가 다르다는 것이 이 결정의 출발점이다.

또 하나의 맥락은 프로젝트의 목표다. 이 프로젝트는 서비스 자체의 완성과 함께, **운영 가능한 수준의 MSA 역량을 확보하는 것**을 명시적인 학습·운영 목표로 삼고 있다. 아키텍처 결정이 순수하게 현재 트래픽만으로 정당화되지 않는다는 점을 숨기지 않는다.

## Decision

처음부터 마이크로서비스 아키텍처를 채택하되, 서비스 수를 다음 6개로 **제한**한다.

- **api-gateway**: 클라이언트 진입점, 라우팅, 공통 관심사(요청 ID 전파 등)
- **member-service**: 회원, 프로필, 인증
- **event-service**: 이벤트 생성, 정원 관리, 신청, 현장 로테이션 진행
- **matching-service**: 선택 수집, 매칭 계산, 결과 관리
- **notification-service**: 매칭 결과 및 안내 알림 발송
- **payment-service**: 참가비 결제, PG 연동

각 서비스는 자체 데이터베이스를 가진다(member_db, event_db, matching_db, notification_db, payment_db). 서비스 간 데이터 직접 접근은 금지하고, 통신은 gateway를 경유한 API 또는 서비스 간 호출로 한정한다.

동시에 다음 원칙을 함께 결정한다. **도메인을 이보다 잘게 쪼개지 않는다.** "이벤트 신청 서비스"와 "로테이션 진행 서비스"를 분리한다든가, 알림을 채널별 서비스로 나누는 식의 세분화는 명확한 운영상 근거가 생기기 전까지 하지 않는다. 서비스 수가 늘어나는 변경은 새 ADR로만 허용한다.

## Reason

**장애 격리가 도메인 특성과 직접 맞물린다.** 이 서비스에서 최악의 시나리오는 이벤트 당일 현장에서 시스템이 멈추는 것이다. 알림 발송은 외부 채널 의존 때문에, 결제는 PG 의존 때문에 우리가 통제할 수 없는 장애를 겪을 수 있다. 이런 장애가 event-service의 로테이션 진행까지 전파되면 오프라인 행사 자체가 무너진다. 프로세스와 DB를 물리적으로 분리해 두면, notification이나 payment가 죽어 있어도 현장 진행은 계속된다. 모놀리스에서도 논리적 격리는 가능하지만, 커넥션 풀 고갈이나 메모리 압박 같은 자원 수준의 전파까지 막아주지는 못한다.

**부하 패턴이 도메인마다 다르다.** 신청 오픈 시각과 이벤트 당일 저녁에는 event-service(그리고 종료 직후 matching-service)에 부하가 집중된다. 반면 member-service나 payment-service의 부하는 상대적으로 평탄하다. 서비스가 분리되어 있으면 부하가 몰리는 서비스만 독립적으로 스케일할 수 있고, 배포도 독립적이라 이벤트 진행 중에 다른 도메인의 배포를 진행하는 것이 현장 리스크가 되지 않는다.

**결제와 인증은 보안 경계가 필요하다.** 결제 정보와 인증 자격 증명은 접근 범위를 최소화해야 하는 데이터다. payment-service와 member-service를 별도 서비스·별도 DB로 두면, 코드베이스 수준의 규율이 아니라 네트워크와 배포 단위 수준에서 접근 경계를 강제할 수 있다. 감사와 보안 강화 작업의 범위도 해당 서비스로 좁혀진다.

**학습·운영 목표.** 솔직하게 말해, 현재 예상 트래픽만 놓고 보면 모놀리스로 충분하다. 그러나 이 프로젝트는 게이트웨이 라우팅, 서비스 간 통신, 분산 환경에서의 관측(요청 ID 전파, 서비스별 로그)과 배포를 실제로 운영해 보는 것을 목표에 포함한다. 이 근거는 기술적 필연이 아니라 프로젝트의 선택이며, 그 비용을 아래 trade-off에서 정직하게 적는다.

## Trade-offs

**운영 복잡도를 크게 산다.** 배포 단위가 6개, 데이터베이스가 5개다. 장애가 나면 어느 서비스에서 시작됐는지 추적해야 하고, 그래서 요청 ID 전파(x-request-id)와 서비스별 헬스 체크 같은 기반 작업이 기능 개발보다 먼저 필요하다. 모놀리스라면 없었을 비용이다.

**분산 트랜잭션과 정합성 문제를 떠안는다.** "결제 완료 후 신청 확정", "매칭 확정 후 알림 발송" 같은 흐름이 서비스 경계를 넘는다. 단일 DB 트랜잭션으로 묶을 수 없으므로 최종 일관성, 보상 처리, 중복·유실 대비 같은 설계 부담이 생긴다. 특히 정원 관리와 결제가 얽히는 신청 확정 흐름은 모놀리스였다면 트랜잭션 하나로 끝났을 문제다.

**로컬 개발 비용이 높다.** 개발자는 여러 서비스와 여러 DB를 함께 띄워야 전체 흐름을 확인할 수 있다. docker-compose로 완화하더라도, 단일 프로세스를 띄우는 것보다 무겁고 느린 것은 사실이다.

**팀 규모 대비 과한 구조일 수 있다.** MSA의 큰 이점 중 하나인 "팀별 독립 개발"은 소규모 팀에서는 실현되지 않는다. 이 이점은 현재로서는 포기한 것으로 간주한다.

이 비용들은 서비스 수를 6개로 제한하고, 경계를 넘는 흐름을 최소화하는 설계로 낮추려 하지만, 없앨 수는 없다.

## Alternatives

**Modular Monolith — 가장 강력한 대안이었고, 기각 이유를 명확히 남긴다.** 단일 배포 단위 안에서 모듈 경계를 엄격히 지키는 구조는 이 프로젝트 규모에서 합리적이다. 트랜잭션 문제가 사라지고, 로컬 개발이 가볍고, 운영 대상이 하나다. 나중에 경계가 검증된 모듈부터 떼어내는 점진적 전환도 가능하다. 그럼에도 기각한 이유는 두 가지다. 첫째, 이 프로젝트의 명시적 목표가 "운영 가능한 MSA 역량 확보"이며, 모듈러 모놀리스는 그 목표를 달성하지 못한다. 둘째, 이 도메인은 경계가 이미 명확하다. MSA의 대표적 실패 요인은 잘못된 경계에서 시작해 경계를 다시 그리는 비용인데, 회원·이벤트·매칭·알림·결제라는 경계는 업무 흐름상 자연스럽고 안정적이어서 그 리스크가 상대적으로 작다. 경계가 불확실했다면 모듈러 모놀리스를 선택했을 것이다.

**순수 모놀리스.** 초기 개발 속도는 가장 빠르지만, 모듈 경계에 대한 강제가 없어 시간이 지나면 도메인 간 결합이 누적된다. 장애 격리와 보안 경계라는 이 도메인의 실제 요구를 코드 규율만으로 지키기 어렵다고 판단해 기각했다.

**세분화된 MSA(십수 개 이상의 서비스).** 신청/로테이션 분리, 채널별 알림 서비스, 인증 전용 서비스 등으로 더 잘게 나누는 안이다. 서비스 수에 비례해 운영·정합성 비용이 늘어나는 반면, 현재 규모에서 얻는 추가 이점이 없어 기각했다. 이 결정의 일부로 "근거 없는 세분화 금지" 원칙을 Decision에 못박았다.

**서버리스(FaaS) 중심 구조.** 신청 오픈 같은 순간 부하에는 어울리는 면이 있으나, 로테이션 진행처럼 상태를 다루는 흐름과 맞지 않고, 팀의 학습 목표(서비스 운영 역량)와도 방향이 달라 기각했다.
