# Pull Request 규칙

PR은 "리뷰 가능한 크기의 변경 + 그 변경이 안전하다는 증거"다.
이 문서는 PR을 만드는 사람과 리뷰하는 사람이 같은 기준을 갖기 위한 규칙이다.

- 상태: 확정
- 최종 갱신: 2026-09-23

리뷰를 **어떻게** 쓰고 답하는지(코멘트 머리표 · AI 리뷰 · 셀프 리뷰 순서)는 [코드 리뷰 가이드](./code-review.md)에 있다.

---

## 0. 흐름 한눈에

```bash
git switch main && git pull                      # 최신 main에서 시작
git switch -c feat/step2-event-api               # 브랜치: <type>/<step>-<topic>
# … 의미 단위로 커밋 …
git push -u origin feat/step2-event-api
gh pr create --base main --fill-first            # 본문은 템플릿을 채운다(아래 2절)
# AI 리뷰(/code-review) → 결과를 PR 코멘트로(코드 리뷰 가이드 5절)
gh pr checks --watch                             # CI 초록 확인
gh pr merge --rebase --delete-branch             # 승인 뒤, 작성자가 머지(6절)
git switch main && git pull
```

- `main`에는 직접 커밋 · push하지 않는다. GitHub 무료 비공개 저장소는 브랜치 보호를 쓸 수 없어 **로컬 `pre-push` 훅**(`.githooks/pre-push`)이 `main` push를 막는다. 켜는 방법: `git config core.hooksPath .githooks`(설치 스크립트가 해 준다).
- **의존하는 PR은 순서대로 하나씩 머지**한다. PR 위에 PR을 쌓지(stack) 않는다 — rebase 머지는 커밋 해시를 바꾸므로 쌓인 PR이 매번 다시 rebase되어야 한다. 앞 PR이 머지되면 최신 `main`에서 다음 브랜치를 딴다.
- **AI 에이전트가 만드는 PR**도 같은 흐름이다. 에이전트는 브랜치를 만들고, 템플릿을 채운 PR을 올리고, AI 리뷰 결과를 코멘트로 남긴다. 머지는 사람이 맡긴 경우에만 한다. 본문 끝에 에이전트가 만들었음을 적고, 커밋 트레일러에는 AI를 적지 않는다.

## 1. PR을 작게

- **한 PR = 한 Step의 한 조각.** 한 Step 전체를 한 PR에 담지 않는다.
- 권장 상한은 **변경 300줄**(생성 파일·lock 파일 제외). 넘으면 쪼갠다. 쪼개는 기준은 [커밋 단위](./branching-and-commits.md#3-커밋-단위--의미-단위로-쪼개기)와 같다.
- 리뷰가 어려울 만큼 크다면 순서대로 의존하는 PR 여러 개로 나눈다(예: 설계서 PR → Contract PR → 구현 PR).
- 설계서(`docs/specs/`)는 **코드 PR과 분리**해 먼저 올린다. 설계서 리뷰에서 방향이 바뀌면 코드는 아직 없는 게 낫다.

## 2. 제목과 본문

- **제목** = 커밋 규약과 같은 형식. `feat(member): 회원 가입 API`. 머지 후 이 제목이 이력에 남는다.
- **본문** = [PR 템플릿](../../.github/PULL_REQUEST_TEMPLATE.md)을 채운다. 항목을 지우지 말고, 해당 없으면 "해당 없음"이라고 쓴다.
- UI 변경은 **스크린샷**(전/후)을 넣는다. 모바일은 iOS/Android 중 확인한 쪽을 명시한다.
- 되돌리기 방법을 한 줄 쓴다. 대개 "`git revert` 가능"이지만, 마이그레이션·환경 변수·외부 설정이 얽히면 절차를 적는다.

## 3. 올리기 전 셀프 체크

PR을 올리는 사람이 먼저 확인한다. 리뷰어의 시간을 아끼는 가장 좋은 방법이다.

| 확인      | 명령 / 방법                                                       |
| --------- | ----------------------------------------------------------------- |
| 빌드      | `pnpm build`                                                      |
| 타입      | `pnpm typecheck`                                                  |
| 린트·포맷 | `pnpm lint`, `pnpm format:check`                                  |
| 테스트    | `pnpm test` (새 로직에는 새 테스트)                               |
| 로컬 동작 | 바뀐 서비스의 `/health`와 관련 엔드포인트를 실제로 호출           |
| 문서      | [문서 갱신 규칙](./documentation-rules.md)의 표에 따라 갱신했는지 |
| 상황판    | 해당 Step 상태를 갱신했는지(머지 직후에 해도 된다)                |
| 커밋 이력 | `wip` 커밋 정리, 각 커밋이 규약을 따르는지                        |
| 비밀      | `.env`, 토큰, 개인정보가 diff에 없는지                            |

- CI가 같은 것을 다시 검사하지만, **CI는 확인 수단이고 셀프 체크는 습관**이다.

## 4. 리뷰어

- **리뷰어 1명 이상.** 머지에는 최소 1개의 승인(Approve)이 필요하다.
- **초기(1인 개발) 동안은 셀프 리뷰를 허용**한다. 순서는 [코드 리뷰 가이드 6절](./code-review.md#6-셀프-리뷰-1인-개발-기간). 단, 조건이 있다.
  - GitHub의 "Files changed" 탭에서 diff를 **끝까지 한 번 읽는다.** 자기 코드를 남의 코드처럼 본다.
  - 템플릿 체크리스트를 빠짐없이 채운다.
  - 팀원이 합류하면 이 예외는 사라진다. 그때 이 문단을 삭제한다.
- 리뷰 요청은 `CODEOWNERS`가 경로 기준으로 자동 지정한다. 필요하면 사람을 추가한다.
- 리뷰 응답 목표: **1영업일 안**. 시간이 없으면 "내일 보겠다"라고 한 줄 남긴다.

## 5. 리뷰 관점 체크리스트

리뷰어는 코드 스타일보다 **경계와 계약**을 본다. 스타일은 Prettier와 ESLint가 본다.

| 질문                                    | 어디를 보나                                                                                                                    |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 서비스 경계를 넘었나?                   | 한 서비스가 다른 도메인의 규칙을 판단하고 있지 않은지. Gateway에 비즈니스 로직이 들어가지 않았는지                             |
| 타 서비스 DB에 접근하나?                | 다른 서비스의 `DATABASE_URL`, 테이블 이름, Prisma 모델을 참조하는 코드가 있는지                                                |
| 공유 패키지에 비즈니스 로직이 들어갔나? | `packages/*` 변경에 도메인 규칙(정원 계산, 매칭 판별 등)이 없는지. Contract(스키마·타입)만 있어야 한다                         |
| Contract를 바꿨다면 소비자도 갱신했나?  | `packages/contracts` 변경 시 이를 쓰는 서비스·`api-client`·프론트엔드가 같은 PR에서 빌드되는지                                 |
| 동기/비동기 선택이 맞나?                | 실패해도 원래 요청이 성공할 수 있는 작업을 REST로 묶어 두지 않았는지(또는 그 반대)                                             |
| 설계서와 일치하나?                      | `docs/specs/SPEC-00N-*.md`에 없는 기능·필드·상태를 임의로 추가하지 않았는지. 달라졌다면 "17. 실제 구현과의 차이" 절에 적었는지 |
| 제품 사실을 지어냈나?                   | 팜플렛·운영 메시지에 없는 기능이나 문구를 만들지 않았는지. 미정은 "결정 예정 (Step N)"으로 표기했는지                          |
| 문서를 갱신했나?                        | [문서 갱신 규칙](./documentation-rules.md) 표에 해당하는 문서가 같은 PR에 있는지                                               |
| 테스트가 의미 있나?                     | 실패할 수 있는 테스트인지. 단순 스냅샷·통과용 테스트는 아닌지                                                                  |
| 되돌릴 수 있나?                         | 마이그레이션·외부 설정이 있다면 되돌리기 절차가 본문에 있는지                                                                  |
| 브랜드 표기                             | "오늘사이" 붙여쓰기, 영문 ONULSAI. "오늘 사이"처럼 띄어 쓰지 않았는지                                                          |

리뷰 코멘트는 머리표(`[필수]` · `[제안]` · `[질문]` · `[사소]`)로 시작하고 **왜**를 같이 쓴다([코드 리뷰 가이드 2절](./code-review.md#2-코멘트-머리표)). "이렇게 바꿔 주세요"보다 "여기서 event_db를 읽으면 ADR-007 위반입니다. member API를 호출해 주세요"가 낫다.

## 6. 머지 방식

> **팀 결정 예정.** 아래는 초기 기본값이다. 팀원이 합류하면 첫 회의에서 확정하고 이 절을 갱신한다.

| 방식                 | 초기 기본값   | 이유                                                                                                                                      |
| -------------------- | ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| **Rebase and merge** | **기본**      | 커밋을 의미 단위로 쪼개는 규약을 지켰다면, 그 커밋들이 `main`에 그대로 남는 것이 가장 가치 있다. 이력이 선형이라 `bisect`·`revert`가 쉽다 |
| Squash and merge     | 예외          | 커밋 정리가 안 된 PR, 또는 커밋 하나짜리 작은 PR에서 선택                                                                                 |
| Merge commit         | 사용하지 않음 | 이력이 갈라져 읽기 어렵다                                                                                                                 |

- Rebase 머지 전 조건: PR의 모든 커밋이 [커밋 규약](./branching-and-commits.md#2-커밋-메시지-규약)을 따르고, 각 커밋이 빌드 가능한 상태다.
- 머지는 **PR 작성자**가 한다(승인이 났고 CI가 초록일 때). 작성자가 부재면 승인한 리뷰어가 한다.
- 머지 후 브랜치는 삭제한다.

## 7. Definition of Done

PR이 머지되어도 아래가 모두 참이 아니면 "끝난 것"이 아니다. 이 표는 **PR 하나** 기준이다. **기능(Step) 하나**가 끝났다는 기준은 [docs/README.md 4절](../README.md#4-한-기능이-끝났다의-정의-definition-of-done)에 있다.

| 항목      | 기준                                                                 | 확인 주체            |
| --------- | -------------------------------------------------------------------- | -------------------- |
| 동작      | `pnpm build` · `typecheck` · `lint` · `test` 로컬 통과, CI 초록      | 작성자               |
| 경계      | 서비스 경계 · DB 소유권 · 공유 패키지 규칙 위반 없음                 | 리뷰어               |
| 계약      | Contract 변경 시 소비자 전부 갱신, 이벤트 스키마 버전 규칙 준수      | 리뷰어               |
| 문서      | 변경 유형에 해당하는 문서를 같은 PR에서 갱신                         | 작성자 → 리뷰어 확인 |
| 설계 일치 | 설계서에 없는 기능을 넣지 않았고, 설계서와 달라진 점은 설계서에 반영 | 리뷰어               |
| 리뷰      | 체크리스트 완료 + 승인 1 이상                                        | 리뷰어               |
| 상황판    | 해당 Step 상태 갱신                                                  | 작성자(머지 직후)    |
| 정리      | 브랜치 삭제, 관련 이슈 닫힘                                          | 작성자               |

## 8. 머지 후

1. 브랜치 삭제.
2. 상황판에서 해당 Step 상태 갱신([시점 기준](./documentation-rules.md#6-상황판-갱신-시점)).
3. `main`에서 CI가 다시 초록인지 확인. 깨졌다면 다른 작업보다 먼저 고치거나 `revert`한다.
