# 코드 리뷰 가이드

- 상태: 확정
- 최종 갱신: 2026-09-23

PR을 **어떻게 읽고, 어떻게 코멘트를 남기고, 어떻게 답하는지** 정한다. 무엇을 보는지(경계 · 계약 · 문서 체크리스트)는 [PR 가이드 5절](./pull-requests.md#5-리뷰-관점-체크리스트)이 원천이고, 이 문서는 그 체크리스트를 쓰는 방식을 다룬다.

## 1. 리뷰 순서

1. **PR 본문부터 읽는다.** 변경 요약 · 관련 설계서 · 되돌리기 방법이 비어 있으면 코드를 보기 전에 채워 달라고 한다.
2. **설계서와 대조한다.** `docs/specs/SPEC-00N-*.md`의 해당 절(API · DB · 상태 머신)을 옆에 띄운다. 설계서에 없는 필드 · 상태 · 엔드포인트가 보이면 그 자체가 코멘트 대상이다.
3. **계약 → 서비스 → 화면 순으로 읽는다.** `packages/contracts`가 바뀌었으면 거기서 시작한다. 계약이 맞아야 나머지를 판단할 수 있다.
4. **테스트를 읽는다.** 테스트가 실패할 수 있는지(깨뜨려 보면 빨개지는지) 본다.
5. **"Files changed"를 끝까지 본다.** 파일마다 "Viewed"를 눌러 빠진 파일이 없게 한다.

## 2. 코멘트 머리표

모든 코멘트는 머리표로 시작한다. 작성자가 무엇을 반드시 해야 하는지 바로 알 수 있게 하기 위해서다.

| 머리표   | 뜻                                       | 머지 전에                                  |
| -------- | ---------------------------------------- | ------------------------------------------ |
| `[필수]` | 버그 · 보안 · 경계 위반 · 설계서 위반    | 고치거나, 고치지 않는 이유에 리뷰어가 동의 |
| `[제안]` | 더 나은 방법이 있지만 지금도 틀리지 않음 | 작성자가 판단. 받지 않으면 이유 한 줄      |
| `[질문]` | 의도를 모르겠음                          | 답변(코드 주석이나 문서로 남길지도 판단)   |
| `[사소]` | 이름 · 오타 · 표기                       | 선택. 다음 PR로 미뤄도 된다                |
| `[칭찬]` | 잘한 점                                  | —                                          |

코멘트는 **무엇이 문제인지 + 왜 + 대안**을 함께 쓴다.

- 나쁨: `이거 바꿔 주세요`
- 좋음: `[필수] 여기서 event_db의 Member를 조인하면 ADR-007(Database per Service) 위반입니다. 이름은 member-service에서 받아 오거나 응답에서 빼 주세요.`

코멘트 대상은 사람이 아니라 코드다. "왜 이렇게 했어요?"보다 "이 분기는 어떤 경우를 위한 건가요?"처럼 쓴다.

## 3. 리뷰 결과

| 결과                | 쓰는 때                                  |
| ------------------- | ---------------------------------------- |
| **Approve**         | `[필수]`이 없거나 모두 해결됨            |
| **Request changes** | `[필수]`이 하나라도 남음                 |
| **Comment**         | `[질문]`만 있어 답을 보고 판단해야 할 때 |

`[제안]` · `[사소]`만 남았다면 Approve한다. 작은 것 때문에 머지를 막지 않는다.

## 4. 작성자가 답하는 방식

- 코멘트마다 답한다. 고쳤으면 **고친 커밋 해시**를 남긴다(`abc1234에서 고쳤습니다`).
- 받지 않은 `[제안]`은 이유를 한 줄로 남긴다. 논의가 길어지면 결정을 PR 본문이나 설계서 17절에 적고 닫는다.
- 대화를 해결(Resolve)하는 것은 **코멘트를 단 사람**이다. 작성자가 스스로 닫지 않는다(셀프 리뷰 기간은 예외).
- 리뷰 반영 커밋은 `fix: 리뷰 반영` 한 덩어리로 뭉치지 말고, 바뀐 내용대로 커밋한다. rebase 머지라 그대로 `main` 이력이 된다.

## 5. AI 리뷰

사람 리뷰를 대신하지 않고 **먼저 걸러 주는 단계**로 쓴다.

| 언제                        | 도구                                                                         |
| --------------------------- | ---------------------------------------------------------------------------- |
| PR을 올린 직후 (모든 PR)    | Claude Code `/code-review` — 버그 · 계약 · 경계. 큰 PR은 `/code-review high` |
| 인증 · 권한 · 개인정보 변경 | Claude Code `/security-review`                                               |
| 과한 추상화가 의심될 때     | `/ponytail-review` (Ponytail 설치 시)                                        |
| 교차 확인(선택)             | Codex 리뷰 — 같은 diff를 다른 모델로                                         |

- AI 리뷰 결과는 **PR 코멘트로 남긴다.** 머리표 규칙을 그대로 따르고, 각 항목 앞에 `(AI)`를 붙인다: `(AI) [필수] ...`
- AI가 낸 `[필수]`도 사람이 확인한 뒤에만 `[필수]`로 취급한다. 틀린 지적이면 이유를 달아 닫는다.
- AI 에이전트가 만든 PR은 본문 끝에 에이전트가 만들었음을 적는다. 커밋 저자는 사람이며 AI를 `Co-Authored-By`로 적지 않는다([브랜치와 커밋 2.5절](./branching-and-commits.md#25-트레일러)).

## 6. 셀프 리뷰 (1인 개발 기간)

[PR 가이드 4절](./pull-requests.md#4-리뷰어)의 예외를 쓸 때의 순서다.

1. AI 리뷰(`/code-review`)를 돌리고 결과를 PR 코멘트로 남긴다.
2. "Files changed"를 끝까지 읽고 PR 가이드 5절 체크리스트를 코멘트로 체크한다.
3. `[필수]`을 모두 해결한 뒤, 머지 직전에 한 줄 코멘트를 남긴다: `셀프 리뷰 완료 — [필수] 0, 남은 [제안] N(이유: ...)`.
4. CI가 초록일 때만 머지한다.

팀원이 합류하면 이 절과 PR 가이드 4절의 예외를 함께 지운다.
